This page lists what sluis v1 does: the checklist for v2 parity. v2 is a rewrite and matches v1 before it adds anything new; parity means that the workloads that use v1 can be wired to v2, possibly in a different way ([Roadmap](/roadmap/)). It is the one page of the site that describes v1 behaviour. The rows were taken from the v1 documentation at release **v1.79.3**; a feature that a later v1 release adds is added when the page is refreshed.

Each row is a GitHub issue labelled [`parity`](https://github.com/truvity/sluis/issues?q=is%3Aissue+label%3Aparity). The roadmap lives in the project's `Product milestone` field ([board](https://github.com/orgs/truvity/projects/9)); the parity rows are in its "v1 parity" milestone, where each issue shows its state. **Changed** says what v2 does instead; **Not in v2** names a part v2 drops. The documentation links go to the [v1 documentation](/v1/).

In v1 a **driver** is the technology behind a port (DynamoDB, KMS, rqlite); in v2 the holders store@, key@ and exporter@ own their drivers ([ADR 0005](/decisions/0005-the-store/#drivers)). An **integration** is a connector to an external system, and a **client** or **relying party** consumes sluis tokens.

| **[Agent-class sessions and consent](https://github.com/truvity/sluis/issues/794)** | Longer chains with 30-minute tokens and a consent page that is never silent. | [How do people and agents differ?](/v1/concepts/sluis/people-and-agents/) |
| **[Recovery sign-in](https://github.com/truvity/sluis/issues/795)** | A way in when no directory can vouch, throttled and audited first. **Changed:** v2 recovery is passkeys only (two attested hardware keys and one pinned synced passkey), with no password and no Kubernetes token check ([Break-glass recovery](/security/break-glass/)). | [What is recovery?](/v1/concepts/sluis/recovery/) |
| **[Web surface hardening and uniform refusals](https://github.com/truvity/sluis/issues/796)** | Security headers, size limits, timeouts, throttles, SSRF-safe fetches and refusals in fixed words. | [HTTP endpoints](/v1/reference/sluis/endpoints/#hardening) |

## Storage and platform interfaces

What sluis depends on for state, secrets, blobs, keys, scheduling and audit transport. In v2 these interfaces are held by store@, exporter@ and key@, and each is a driver private to its holder.

| Feature | What v1 does | v1 documentation |
|---|---|---|
| **[Versioned state](https://github.com/truvity/sluis/issues/797)** | Versioned key-value state with TTL, compare-and-swap and watch, on DynamoDB, Kubernetes or memory. **v2:** the durable and temp kinds behind store@, with `if_version` updates, a mandatory TTL on temp kinds and watch from a resume point, on DynamoDB or rqlite ([ADR 0005](/decisions/0005-the-store/#the-store-api)). | [Ports](/v1/reference/sluis/ports/) |
| **[Own and integrations' secrets, and typed export](https://github.com/truvity/sluis/issues/798)** | sluis's own and its integrations' secrets (SSM, OpenBao KV v2, Kubernetes Secrets, memory), and typed credential documents for consumers. **Not in v2:** the OpenBao KV v2 store; v2 has no OpenBao. **v2:** a secret that sluis generates or receives is sealed or hashed durable data, the secrets an operator provides come from a secret source (a systemd credential or SSM), and exporter@ publishes only the kinds marked exportable ([ADR 0004](/decisions/0004-the-data-model/#treatment), [ADR 0009](/decisions/0009-export/)). | [Ports](/v1/reference/sluis/ports/) |
| **[Blob storage](https://github.com/truvity/sluis/issues/799)** | Reports and snapshots in S3, the legacy store or memory. **v2:** the blob is the audit family's own port, for the audit log; backups go to a bucket through exporter@ ([ADR 0029](/decisions/0029-the-audit-log/#projects)). | [Ports](/v1/reference/sluis/ports/) |
| **[Token signing and key ring](https://github.com/truvity/sluis/issues/800)** | Token signing with a file key, AWS KMS keys or a KMS-wrapped key ring. **v2:** key@ signs in place with a KMS key or a card, and there is no key ring ([ADR 0006](/decisions/0006-keys-and-sealing/#keys-sign-in-place)). | [How does sluis sign tokens on AWS?](/v1/concepts/sluis/signing-on-aws/) |
| **[Platform scheduler and lease](https://github.com/truvity/sluis/issues/801)** | Controller ticks under a lease, from a ticker or EventBridge Scheduler. **v2:** one reconciler per target under a lease (a temp kind) with a fencing token, ticked by a timer, a scheduler or a wake ([ADR 0026](/decisions/0026-reconcilers/#scope), [ADR 0005](/decisions/0005-the-store/#leases)). | [Ports](/v1/reference/sluis/ports/) |
| **[Audit transport](https://github.com/truvity/sluis/issues/802)** | Audit records to an audit installation over Connect or SQS. **v2:** direct, spool, SQS or NATS JetStream ([ADR 0028](/decisions/0028-audit-pieces/#transport)). | [Adapters](/v1/reference/sluis/adapters/) |
| **[Driver selection and registry](https://github.com/truvity/sluis/issues/803)** | Adapters chosen from named presets. In v2 the named sets are the tested installations ([ADR 0011](/decisions/0011-runtimes-and-installations/#installations)). | [Adapters](/v1/reference/sluis/adapters/) |
| **[State migration between storages](https://github.com/truvity/sluis/issues/804)** | State, secrets and reports copied between stores with a dry run, a read-back check and rollback. **Changed:** there is no `sluis migrate`; a backup and a restore into the new installation move state between drivers ([ADR 0010](/decisions/0010-backup-and-recovery/#restore)). | [Move the State with `sluis migrate`](/v1/guides/sluis/migrate/migrate-state/) |
