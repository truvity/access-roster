A sluis release publishes every artifact from `https://distribution.sluis.id/`, a Cloudflare R2 bucket, with no redirects. GitHub Releases holds the same files as the immutable record. Every artifact of a release carries the same version and ships together. The design is [0013](/decisions/0013-release-train-packaging-and-distribution/); how to check what you downloaded is [Release signing](/distribution/release-signing/).

## At a glance

- **One version for the whole repository.** A release is built with GoReleaser v2, open-source edition, which includes the Rust builds ([0013](/decisions/0013-release-train-packaging-and-distribution/#one-version)). The YubiKey driver and the build of key@ that links `piv-go` need cgo against pcsc-lite, so they are built in a native per-architecture CI job.
- **Packaging follows the runtime, for amd64 and arm64.** There are no build profiles, and `dev` is not a build; it is how the local installation is run ([Packaging per runtime](#packaging-per-runtime)).
- **Packages follow the holders and the modules.** A host installs the foundation (store@, key@ and exporter@), the modules it runs, and only the drivers it uses ([Packages by holder and module](#packages-by-holder-and-module)).
- **Two homes.** `distribution.sluis.id` is a Cloudflare R2 bucket in the same account as the sluis.id zone. Everything is served from R2 with no redirects, and GitHub Releases keeps the same files as the record.
- **Checksums and SBOMs from the first alpha, no signed artifact.** Every release from `v2.0.0-alpha.1` carries checksums and SBOMs. The signing of release artifacts, keyless or OpenPGP, is in Backlog (decided on 2026-11-07), and the maintainer signs each tag by hand ([Release signing](/distribution/release-signing/)).
- **Nothing is stable before v2.0.0.** Releases until then are `v2.0.0-alpha.N` pre-releases, with no `latest` tag on images or charts.
- **No static upload key.** Images and GitHub Releases are published with the workflow's own token. Uploads to R2 wait until a sluis installation can mint them: CI then exchanges its GitHub OIDC token with sluis for a short-lived R2 token ([How CI uploads](/distribution/release-signing/#how-ci-uploads)).
- **The website is separate.** `sluis.id` is served as static assets on Cloudflare Workers, deployed by GitHub Actions, with a small live status API beside it ([0014](/decisions/0014-the-site-is-static-on-cloudflare-workers/)). Only distribution is on R2.

### Why R2 and no redirects

apt and dnf handle redirects unreliably, and a redirect chain is one more place for a repository to be pointed somewhere else. Serving every path directly from one bucket keeps the URL a user pins and the file they get the same thing. GitHub Releases is the second copy, and the one to compare with if the first is in doubt.

## Supported platforms

| Distribution | Version | systemd | Packages from |
|---|---|---|---|
| Ubuntu | 26.04 LTS | 259 | the apt repository |
| Rocky Linux | the latest stable, 10.x | 257 (10.2) | the dnf repository |
| Amazon Linux | 2023 | 252 | the dnf repository |

- **All of them on amd64 and arm64.**
- **The systemd floor is 252,** the version in Amazon Linux 2023. Generated units may rely on what 252 provides, such as `LoadCredentialEncrypted=` and `ExecPaths=`.
- **Serverless and Kubernetes have no host distribution.** An executable that needs cgo is built against the oldest supported glibc, so the same binary runs in a package and in an image.
- **A board image older than the floor is a declared exception,** not a supported platform: the boards deploy refuses to write a credential on it (the units read `LoadCredentialEncrypted=`), and `sluis doctor` warns where its kernel fails the randomness checklist. The boards themselves run Ubuntu 26.04 and Rocky 10 since 2026-11-06 ([Bare-metal](/runtimes/bare-metal/#ubuntu-2204-boards-are-gone)), so no board needs the exception. Key material is never affected: it stays in the card.
- **No FIPS build in v2.0.** Every platform gets the same build, and the algorithms stay in the FIPS-approved set so that a variant can be added when a customer needs it ([0006](/decisions/0006-keys-and-sealing/#algorithms)).

## Packaging per runtime

There are no build profiles: the runtime decides the packaging, and every artifact is built for amd64 and arm64. `dev` is not a build; it is the local installation, which runs the published images under Docker Compose.

| Runtime | Packaging |
|---|---|
| [bare-metal](/runtimes/bare-metal/) | `.deb` and `.rpm` packages split by holder, module and driver, in apt and dnf repositories, and a tarball |
| [serverless](/runtimes/serverless/) | A zip per executable, a function per actor instance, at most three sluis layers per function |
| [kubernetes](/runtimes/kubernetes/) | One multi-arch OCI image per process, and one Helm chart with the images pinned by digest |

The install directory is the same in a package, a tarball and an image:

```text
/usr/libexec/sluis/{actors,drivers,node,vendor}/<short-name>
```

The adapters are actors. A driver sits in the private directory of its owner, `drivers/<owner>/<name>`, where the owner is the actor whose port it serves.

## Packages by holder and module

Every driver executable is a package of its own, so a host installs only what it runs. A driver belongs to one holder and is private to it ([0005](/decisions/0005-the-store/#drivers)), so what a host installs follows the holders and modules it runs.

| Package | Holds |
|---|---|
| `sluis-cli` | The command-line tool at `/usr/bin/sluis`: `sluis agent`, `sluis trust sync`, and `sluis key request`, `install` and `status`. No dependency on systemd, so a workstation installs it alone |
| `sluis` | The foundation's `policy` and `entry` (whose executable the audit front also runs), with both units of `entry`, the identity front and the audit front, the timer of `sluis trust sync` ([Identity](/concepts/identity/)) and their units; depends on `sluis-cli` and on systemd |
| `sluis-node` | The node agent |
| `sluis-store`, `sluis-key`, `sluis-exporter` | The foundation: each holder with its units |
| `sluis-driver-<owner>-<name>` | One driver executable (for example `sluis-driver-store-rqlite`), with the system packages it needs; named like its [image](#oci-images) and its tarball |
| `sluis-identity` | The identity module: the work actors other than `quota`, `policy` and `entry`, the first-party adapters included |
| `sluis-console` | The console's static bundle |
| `sluis-audit-writer` | The audit module: the writer and the witness |
| `sluis-audit-search` | The audit module: the indexer and the reader |
| `sluis-quota` | The quota module |
| `sluis-host` | The root host service, mainly for [SSH](/integrations/infrastructure-access/#ssh); it never listens on the network |
| `sluis-install-boards` | The meta-package of the boards installation |

Examples of driver packages:

| Package | Dependencies and contents |
|---|---|
| `sluis-driver-key-yubikey-piv` | (not built yet: the card driver comes from the native job) Depends on pcscd, a CCID driver (`libccid`, `pcsc-lite-ccid`), libpcsclite (`libpcsclite1`, `pcsc-lite-libs`) and polkit (`polkitd`, `polkit`); Suggests `yubikey-manager`. On a node the card service serves key@ only ([0006](/decisions/0006-keys-and-sealing/#exclusive-card-access)) |
| `sluis-driver-store-rqlite` | Ships `rqlited` under `vendor/` (not built yet: the package holds the driver alone) |

Every dependency of every form, with the package names per family, is in the [runtime dependency matrix](/distribution/dependencies/).

- **A driver package depends on the package of its owner** and, in one case, recommends the driver package of another owner. The indexer's file driver reads the audit blob that the writer's file driver serves, so its unit requires the writer's driver, which is in another package; `sluis-driver-indexer-fs` has `Recommends: sluis-driver-writer-fs` at the exact version, in the plan as the one weak edge (`WeakEdges`) and the only one the check allows. A recommends is installed by default and may be left out, so the walk of REQ-SUPPLY-029 (an audit host installs no identity actor) follows it too; the meta-package of the boards installs both, and `sluis doctor` will name a missing one (not built yet). A driver package still depends on no other driver package, and no package depends on one. It installs no service for an operator to start: the owner's unit starts the driver, and only the owner can open its socket ([0003](/decisions/0003-units-transports-and-fusion/#units)).
- **A module package depends on the foundation packages and on no other module,** and no package depends on a driver package it does not use. A host that runs the foundation with the audit module only installs no work actor of the identity module and no driver it does not run, and a KMS-only host installs no card driver and no pcscd.
- **Meta-packages exist only for the bare-metal installations that install from packages.** The local installation runs images and uses software keys by default, so it needs no package and no meta-package.
- **Template units only.** The packages ship `sluis-<actor>@.service` and `sluis-<actor>@.socket` and a systemd generator that creates the instances ([Bare-metal](/runtimes/bare-metal/#what-runs-where)). sluis generates no per-installation packages.
- **The console is a separate artifact,** a bundle of static files built once per release and served same-origin with the API: a directory from `sluis-console` on bare-metal, the bucket behind the API gateway on serverless, its own Deployment on Kubernetes. The audit console is a bundle of its own on the same train, served on the audit front's origin ([0028](/decisions/0028-audit-pieces/#the-audit-front), [#985](https://github.com/truvity/sluis/issues/985)).
- **The trust bundle reaches hosts through the `sluis` package.** `sluis trust enroll` turns on `sluis-trust-sync.timer`; the sync checks the bundle and the root list, writes the anchors and runs the distribution's trust update ([0013](/decisions/0013-release-train-packaging-and-distribution/#packaging-per-runtime)). On Kubernetes the bundle reaches pods through a trust-manager source or a ClusterTrustBundle.
- **Root ceremonies are not part of sluis.** They belong to [ritueel](https://ritueel.id). The release keyring package that apt and dnf verify with is built with ritueel's tools and published in sluis's own repositories, once the roots exist ([Release signing](/distribution/release-signing/#the-openpgp-release-key)).

## The R2 layout

The distribution site (#873), with its apt and dnf repositories, is v1 parity (decided 2026-11-07). The first working version publishes images, tarballs, checksums and SBOMs from GitHub Releases, and the layout below is the design for the site.

```text
apt/       dists/stable/{InRelease,Release,Release.gpg}
           dists/stable/main/binary-{amd64,arm64}/
           pool/
dnf/       {x86_64,aarch64}/{repodata/, packages}
           sluis.repo
bin/       <version>/<component>_linux_{amd64,arm64}.tar.gz
lambda/    <version>/{functions,layers,extensions}/sluis-<kind>-<name>_<version>_{arm64,x86_64}.zip
checksums/ <version>/SHA256SUMS, and SHA256SUMS.asc once releases are signed
keys/      the release keyring, once the roots exist
latest     pointer to the newest version
```

- The repository metadata files (`InRelease`, `Release.gpg`, `repomd.xml.asc`) are not signed, because the signing of release artifacts is in Backlog; a repository cannot be verified by its signature.
- `latest` points to the newest version. Pin a version in anything you automate.

## apt (Debian and Ubuntu)

The apt repository is v1 parity (decided 2026-11-07), with the rest of the distribution site.

Until releases are signed, download the `.deb` files and `SHA256SUMS` from the GitHub release and check them ([Release signing](/distribution/release-signing/#a-release-before-it-is-signed)). Once the apt metadata is signed, add the repository with the release keyring:

```sh
# Example
echo "deb [arch=$(dpkg --print-architecture) signed-by=/usr/share/keyrings/sluis-release.gpg] https://distribution.sluis.id/apt stable main" \
  | sudo tee /etc/apt/sources.list.d/sluis.list
sudo apt update && sudo apt install sluis
```

The repository has one suite, `stable`, and one component, `main`. `signed-by` scopes the keyring to this one repository. How you get the keyring and check it is in [Release signing](/distribution/release-signing/#the-openpgp-release-key).

## dnf (Rocky Linux and Amazon Linux)

The dnf repository is v1 parity (decided 2026-11-07), with the rest of the distribution site.

```ini
# Example: /etc/yum.repos.d/sluis.repo
[sluis]
name=sluis
baseurl=https://distribution.sluis.id/dnf/$basearch
enabled=1
repo_gpgcheck=1
gpgcheck=0
gpgkey=file:///etc/pki/rpm-gpg/sluis-release.asc
```

`$basearch` is `x86_64` or `aarch64`. `repo_gpgcheck=1` verifies the signed `repomd.xml`, which carries each package's checksum. Header signatures on each rpm come later ([0024](/decisions/0024-root-custody-and-the-signing-api/#the-signing-api)); then the file sets `gpgcheck=1` as well. Before the metadata is signed, verify downloaded `.rpm` files against `SHA256SUMS`.

### How the packages are built

`tools/release/packages` builds the `.deb` and the `.rpm` of every package, for amd64 and arm64, with the nfpm library, from the executables of the archives of the same run, byte for byte (`just release-packages`; the checks of its code are `just check-packages`). It is a Go module of its own, so nfpm and its dependencies are in no other build. The plan, the reader and the check are a library, `tools/release/pkgs`, with no dependency but the standard library and yaml (a test holds it to that); `tools/release check-packages` runs the check, so the job that publishes, which compiles `tools/release`, never links nfpm. GoReleaser's own `nfpms` step is not used: it writes `dependencies` as they are, so `{{ .Version }}` stays in the file, and both formats then ship a dependency that is never met (MEASURED 2026-11-07, GoReleaser 2.20.0).

- **The packages are the ones the images list and the actor registry give.** An executable of `deploy/release/images.yaml` joins a package without anyone listing it: the data and keys families are `sluis-store`, `sluis-key` and `sluis-exporter`; the work actors other than `quota`, `policy` and `entry` are `sluis-identity`; the audit family is `sluis-audit-writer` and `sluis-audit-search`; a driver is `sluis-driver-<owner>-<name>`; the package `sluis-cli` holds the command-line tool, at `/usr/bin/sluis` (which finds the store helper at `../libexec/sluis/actors/store` beside it) and depends on no systemd, and the base package `sluis` holds the foundation's `policy` and `entry`, which the exporter, the audit module and quota start with and whose executable the audit front runs, and depends on `sluis-cli` and systemd (decided 2026-11-08). A workstation installs `sluis-cli` alone; the CLI-only install was proven with `apt` on Ubuntu 26.04 and `dnf` on Rocky Linux 10 and Amazon Linux 2023, with no systemd added. A package with no executable is not built. Not built yet, and why: the card driver (the native job), `sluis-node`, `sluis-host`, `sluis-console` and the meta-package of the boards.
- **One version, mapped once.** `2.0.0-alpha.1` is `2.0.0~alpha.1` in both formats, because a tilde sorts before the release (dpkg, and rpm 4.10 and later), and a dash would be read as the revision of a `.deb`. Every dependency of a package on another package of the release is `= 2.0.0~alpha.1`: `sluis-store (= 2.0.0~alpha.1)` in a `.deb`, `sluis-store = 2.0.0~alpha.1` in an `.rpm`. A pre-release with a hyphen or a build metadata is refused.
- **The file names keep the dash:** `<name>_<version>_<arch>.deb` and `.rpm`, with the version as tagged and the `.rpm` architecture `x86_64` or `aarch64`. Whether GitHub keeps a `~` in an asset name is UNVERIFIED, and the package manager reads the version from the metadata, so the name does not need it. `SHA256SUMS` beside the packages lists them; adding it to the release's is the release job's.
- **One `.deb` serves Ubuntu 26.04, and one `.rpm` serves Rocky Linux 10 and Amazon Linux 2023,** whose rpm 4.16 is the floor: the payload is gzip, the file digests are SHA-256, and the check refuses a package that asks rpm for a feature that 4.16 lacks (the list is `rpm --showrc` on Amazon Linux 2023, MEASURED 2026-11-08). The same sixteen packages installed with `apt` and `dnf` on the three systems on that day, from a directory, with the dependencies resolved.
- **Units, users and directories.** A package ships the template units of the executables it holds (`/usr/lib/systemd/system/sluis-<x>@.service`, the same file for every boundary), its own `sysusers.d` file and its own `tmpfiles.d` file, named after it, all generated by `tools/gen/units` into `deploy/boards/units` and read from there (`pkgs.AttachUnits`). A unit whose executable no package holds yet (the console, quota, the adapters, the SSH CA) is in no package: a unit that cannot start is not shipped, and the check holds each unit's `ExecStart=` to an executable of the same package. A package makes the users and groups it owns and **declares every other group its units join** (`SupplementaryGroups=`): a `g <name> <gid>` line in its own `sysusers.d` file, with the number of the uid plan, for each group of a callee, of the drivers a unit owns or of its owner, and of the forwarder, so a unit starts on a host that has the package and its `Depends` and not the packages that own those groups (without the line, systemd refuses the unit with status 216/GROUP). The callee still owns its sockets, its directories (`tmpfiles.d`) and its users; only the existence of a group is shared. `systemd-sysusers` makes a group that is missing and leaves one that exists, so the package installed first makes it and the others change nothing (the units need no membership line); every declaration of a group, in any package, is the same name with the same number, and a user is made by exactly one package (REQ-SUPPLY-050, 051). A package never deletes a user or group. **Drift on the host is silent.** `systemd-sysusers` keeps a group that already exists with another number, and takes a number of its own choosing when the pinned one is used by another name, and it says nothing; the units name groups by name, so they still start, but the programs get the pinned numbers (`--socket-gid` and the like), so a host whose group has another number serves a socket to the wrong group. The packages cannot prevent that, and nothing in them detects it yet; the boards' deploy refuses it (`check_pinned_ids`), and a `sluis doctor` check of the same kind for a package host is proposed in [issue 1755](https://github.com/truvity/sluis/issues/1755). Deriving `Depends` from the groups was refused: it gives 35 cycles and makes the base package depend on modules (REQ-SUPPLY-029). The users and directories are those of the boundary `dev`, with the pinned uids, as the generator makes only that one; `sluis node apply` will render the files of the boundary an installation names (later work). The uid plan (`/etc/sluis/uids-<boundary>.env`), the bootstrap file and the credentials are installation data: no package writes them, and the install tier places the first two as `node apply` will. The maintainer scripts of a package with units are three, one text for the `.deb` and the `.rpm`: `postinst` makes the package's users and directories from its own two files, tells systemd and, when a version is already installed, restarts the instances that run (`try-restart`, which never starts a stopped unit); `prerm` stops the package's instances on a removal and never on an upgrade; `postrm` tells systemd. They need a running systemd for the systemd steps, so an image build or a chroot installs them. They delete nothing: a removal, and a `.deb` purge, leave `/etc/sluis`, `/var/lib/sluis-state` and every user.
- **Files:** executables 0755, everything else 0644, directories 0755, all owned by root, no setuid, setgid or sticky bit, nothing in `/opt`, `/usr/local`, `/etc/sluis` or `/var/lib/sluis-state`. A package never deletes state or users (the maintainer decided on 2026-11-08), so a maintainer script starts, enables and deletes nothing. A package's users and directories are in `/usr/lib/sysusers.d/<package>.conf` and `/usr/lib/tmpfiles.d/<package>.conf`, so a script reads its own file and no other. The same inputs give the same bytes.

`tools/release check-packages` reads the built files back, with its own reader, which was compared with `dpkg-deb` and `rpm` for the same packages. It checks the version and the dependencies of each package (exact, in the syntax of the format, and only the external dependencies that [the matrix](/distribution/dependencies/) lists), the modes and owners, that each executable is the file of its archive and a static ELF of its architecture with the version in it, that the layering of the dependencies is the one of [Packages by holder and module](#packages-by-holder-and-module) (the CLI depends on nothing of the release, `sluis` on the CLI, the foundation on `sluis`, a module on `sluis` and the foundation and on no other module), that a host with `sluis` and the audit packages installs no identity actor (read from the executables the packages hold), that every group a unit of a package joins is declared in the package's own `sysusers.d` file, that every declaration of a group is the same in every package and a user is made by one package (read from the built `.deb` files), that the maintainer scripts start, enable and delete nothing and name only files of their package, that a driver package holds no unit an operator can enable, and that a `.deb` and an `.rpm` of one package hold the same files, scripts and dependencies. The read-back is a closed set: a `.deb` has only the control fields the check reads (no `Provides`, `Conflicts`, `Replaces`, `Breaks`, `Pre-Depends` or custom field) and the three ar members; an `.rpm` has only the header tags it reads (no provides beyond itself, no conflicts, obsoletes, triggers, pretrans or posttrans), its payload is read and each file in it is the one the header lists, and its release is 1 (a `.deb` has no revision); directories only below the places a package installs into or above them. Every archive the reader inflates is read through a cap (1 GiB for a data archive or a payload, 8 MiB for a control archive), the sizes in the entries' headers are held to it and to their sum, a sparse entry is refused (its holes cost no byte of the stream), and an rpm header is held to a store of at most 64 MiB, to the data its counts point to, to sums of what its entries claim (strings at most a quarter of the store and 4096, and at most 262144; numbers at most the store and 4096, and at most 16 MiB), checked before a slice is built, and to one budget for the walks over its strings, so a crafted package is an error and not an exhausted job. A package has no maintainer script that the plan does not list, and the plan lists the three scripts above for a package with units. The text of a planned script may run only what is on a short list (`exit`, `set -e`, `[`, `test`, `echo`, `true`, `systemctl daemon-reload`, `systemctl stop` or `try-restart` of a sluis unit, `systemd-sysusers` and `systemd-tmpfiles --create` on files of `/usr/lib`, and the words of `if` and `case`), with no command substitution, heredoc or redirect but to `/dev/null`; anything else is a refusal, and a list of refused words only explains it. The script is printable ASCII, newlines and tabs (a shell's blanks are the space and the tab; a no-break space, a form feed or a CR is a blank to Go's `strings.TrimSpace` and a word to a shell). The shape of the text is held to the part of the shell where reading it a line at a time is true: the first line is `#!/bin/sh`, with at most `-e` or `-eu`, because the rest of a shebang line reaches the interpreter; a `#` only starts a line (no comment after a command, no `$#`, no `${#a}`); no line ends with a backslash; no `$'` and no `$"`; a `${` is `${NAME}` and nothing else; and no quote is open at the end of a line. A test feeds every short line made of the pieces that bend the reading of the next line to the shells of the host (dash, sh, bash), after each a line that the lint takes for a comment and a shell would run, and asserts that nothing the lint accepts runs it. That is still text: it cannot see everything a shell can do, and the proof is the install tier. The proof is the install tier ([below](#the-install-tier)), which watches the units and the state across install, upgrade, removal and reinstall.

### A throwaway repository for tests

`just release-repo` makes an apt repository and a dnf repository of the packages of `dist/packages` in `dist/repo`, `just release-repo-serve` serves them on a loopback address, and `just release-repo-smoke` installs `sluis-cli` and `sluis` from them in containers. **They are not the publication site.** The trees are unsigned (no `InRelease`, `Release.gpg` or `repomd.xml.asc`; a client is told to trust them with `[trusted=yes]` or `gpgcheck=0`), each carries `UNSIGNED-TEST-REPOSITORY.txt` to say so, and the server refuses any address that is not a loopback IP address. The site on R2 stays in v1 parity, signed ([The R2 layout](#the-r2-layout)).

- **The metadata is written in Go, from the packages themselves,** by `tools/release/repo`, with the standard library and the readers of `tools/release/pkgs`: no `createrepo`, `dpkg-scanpackages` or `apt-ftparchive`. The apt tree is `pool/main/<letter>/<name>/<file>`, `dists/stable/main/binary-{amd64,arm64}/{Packages,Packages.gz,Release}` and `dists/stable/Release` (SHA-256 and SHA-512 of every index file). The dnf tree is one directory per `$basearch` (`x86_64`, `aarch64`) with `Packages/` and `repodata/` (`repomd.xml`, `primary`, `filelists` and `other`, gzip, named by their checksum), with the header range, every dependency with its flags and version, and the file lists. The same packages and the same date give the same bytes; with no date given, the date is the newest build time of the packages (the commit time), held a minute below the clock, and a date in the future is refused.
- **The repository carries the bytes that were checked.** The builder refuses a package whose SHA-256 is not the one in the `SHA256SUMS` beside it, and a package the sums do not list. It then reads its own output back by another path (a parser of `Packages` and `Release`, and the XML decoder of the standard library) and fails on any disagreement with the files: a size, a hash, a count, a file that no index lists, a signature file, a file that is not a regular file, a package whose name, version or architecture differs from the entry that names it, a location outside `Packages/`, the same package twice, and a dependency on a package of the release that is not met in the tree of its architecture at the exact version. The server opens the directory with `os.OpenRoot` and serves regular files only: a link is a 404, whatever it points at.
- **It stays out of the job that publishes.** The code is `tools/release/repo`, the command is `packages repo` and `packages serve` in the module of the builder, and `tools/release` links none of it (`tools/release/imports_test.go` refuses the import). Nothing in it needs a token.
- **The smoke installs from the repository and from nothing else** (`tools/release/repo-smoke.sh`). For each of Ubuntu 26.04 (apt), Rocky Linux 10 and Amazon Linux 2023 (dnf), by digest, a container on the host network with nothing mounted installs `sluis-cli` alone (and no systemd comes with it), and another installs `sluis` alone, so that apt or dnf resolve `sluis-cli` at the exact version through the repository and take `systemd` from the distribution. Each then checks the installed version, the files, that no unit was enabled, and that the package manager names the repository as the source; with `SLUIS_SMOKE_EXPECT_VERSION` (the recipe sets it from `dist/release/metadata.json`) it runs `sluis version`. The log of the server must show the `.deb` or `.rpm` requests of both packages. The release rehearsal of CI runs it after `release-packages`.
- **What this does not prove.** Not signed metadata, not what an upgrade, a removal or a reinstall does, not units or credentials (the containers have no running systemd), and not the site. The smoke installs on the architecture of its host; the lifecycle, on both architectures, belongs to the install tier.

### The install tier

`deploy/verify` installs the packages from the throwaway repository into systemd containers and watches what happens, on **Ubuntu 26.04, Rocky Linux 10 and Amazon Linux 2023, on amd64 and on arm64** (a hosted `ubuntu-24.04-arm` runner), in the job `install` of `candidate.yaml`, which `checks.yaml` calls as the candidate's rehearsal ([The release candidate](#the-release-candidate)). It runs when the packaging, the units, the tier, the release tools or those workflows change, and on every push to `main`. It is the lifecycle of the plan of 2026-11-08 (the owner decisions D4 and D7) made into a test, and the evidence of it is the first part of the report a release carries (REQ-TEST-017).

- **The systems.** `nodes.tsv` lists them: the base image by the digest of its multi-architecture index, and a Dockerfile that adds what systemd needs as an init and what the packages declare (systemd and ca-certificates) and nothing of sluis. The test switches the distribution's own repositories off, so a dependency the packages forgot to declare is found. The repository (both releases, as a real one holds them) is served by the container's own process on its own loopback address, and the container has no network.
- **The previous release.** No release has published packages, so `previous.sh` takes the archives of the previous release from its GitHub release, holds each to the sums of that release and packages them with this tree's packaging. The executables are the previous release's, byte for byte; the units and scripts are this tree's, so the upgrade tests an upgrade of the executables and not a change between two packagings. The release under test is a pre-release above the latest tag (`versions.sh`: the next alpha, or the first alpha of the next patch after a stable release), so that the upgrade goes up. `previous.sh` fetches over https only and holds the published `SHA256SUMS` to the hash committed in `deploy/verify/previous.sums`; that file gets a line for each release when it becomes the previous one.
- **The steps** (`lifecycle.sh`), in a fresh container: **install** (every package at the exact version, exit status and, for dnf, whose exit status cannot be trusted, its output; no package half configured, `dpkg -V` or `rpm -V` silent; the users, groups and directories of the packages exist with the numbers the files give; nothing started and nothing enabled; the executables run and say the version; `sluis doctor` passes), **serve** (the uid plan and the bootstrap file placed as `node apply` will, `systemd-analyze verify` of every unit, the standalone drivers started, still up after four seconds, not restarted, under their own uid with no capability and no new privileges, and their sockets accept a connection), **remove** (the instances stopped, the executables and units gone, `/etc/sluis`, the state and the users exactly as before, and on Ubuntu a purge too), **reinstall** (the packages again, the users unchanged, the files of the kept state still there, and the spool driver recovers the spool the first run made) and **downgrade**; in a second container **upgrade**: the previous release installed and serving, then this one over it, the running instances replaced by new processes; and in a third container **minimal**: only `sluis` and `sluis-store` are installed, with no recommended package and no driver package, and the groups that their units join exist with the numbers the files give (`getent group`, decision 25-D), and `systemd-analyze verify` passes for their units (the lines about the driver units that are not installed are left out).
- **What blocks.** Every step blocks on a failure. The upgrade and the downgrade also have a third result, `refused`: the packages are not installed or do not serve, and the package manager or the service says why ("installs and serves, or refuses with a named reason", owner decision D4 of 2026-11-08; ADR 0013 and 0015 promise no compatibility between alphas). A refusal with its reason passes the gate and is reported with that reason; a failure, or a refusal that names nothing, blocks. A passing upgrade or downgrade must have downloaded the other release's packages (the server's log shows it), and an instance that ran before must have a new process after it.
- **Only the drivers that stand alone start** (the audit spool driver and the software key driver). The actors need a signed configuration, a store and an engine, which the full tier supplies and which is not built. So no actor is shown to serve here, only that its unit verifies and its executable runs.
- **The evidence** is `evidence-<arch>.json`, written by `tools/verify evidence-write` from what the run left and checked by `evidence-check`; its shape is `deploy/verify/evidence.schema.json` (version 1). It names the release and the previous one with the digest of every package file, and for each architecture the systems (image by digest, the kernel and systemd it ran on, the package files the system downloaded, by the server's own log) and one result for each step on each system: `pass`, `fail`, `refused` or `not_run`, with the requirement rows the step claims, a reason unless it passed, the versions the package manager says are installed after the step, and the log. A report is complete when every step has a result on every system of every architecture asked for, a result that is not a pass says why, and every download is a package the report lists with that digest; a step the run did not reach is `not_run` and says which step failed before it. The job keeps the report and the logs as an artifact. Merging the reports of the architectures, attaching them to the release and gating on them are the release workflow's.
- **The test bites.** `mutants.sh` breaks one `.deb` at a time in the ways a maintainer script must not (it deletes the state, deletes a user, starts a unit, enables a unit, leaves an instance running, fails) and the job fails if the lifecycle lets one through. One mutant takes the declaration of a store driver's group out of `sluis-store`'s `sysusers.d` file (the file and its `md5sums` rewritten, so `dpkg -V` stays silent): only the step `minimal` may fail.
- **It runs in GitHub CI only.** The containers need systemd's cgroup (`--privileged` and the host cgroup, as the other systemd tests of this repository use; MEASURED 2026-11-09 on a workstation: a container with a private cgroup namespace boots no systemd, with or without `CAP_SYS_ADMIN`, because its cgroup is read-only) and the scripts of the packages run in them. So `run.sh`, `lifecycle.sh` and `mutants.sh` refuse to run unless both `GITHUB_ACTIONS=true` and `RUNNER_ENVIRONMENT=github-hosted` are set (a self-hosted runner says `self-hosted`, and one variable alone is a word anyone can export), or `SLUIS_VERIFY_EPHEMERAL_VM=1`, the explicit word of someone who has a virtual machine that is thrown away. Neither is a proof that the machine is disposable; they keep a workstation from running it by accident.
- **What it does not prove.** The containers share the runner's kernel, so not the kernels of the systems, SELinux, a real boot with the generator, or `LoadCredentialEncrypted=` on Rocky Linux and Amazon Linux (the credentials directory of a unit is empty there in a container, MEASURED 2026-11-07); those are the virtual machine tier. Not a signed repository. Not a mixed three-node cluster. Not the card.
- **Amazon Linux 2023 has systemd 252, which does not know `RestartSteps=` and `RestartMaxDelaySec=`** (added in 254), which every generated unit uses. systemd ignores them with a warning, and a unit that fails then restarts every two seconds with no back-off and, having no start limit (REQ-DEPLOY-044), for ever. The serve step filters exactly those two unknown-key warnings of `systemd-analyze verify` on a systemd older than 254, and records that as a note of its result, so on that system the verify is clean of everything else only; the floor of 252 and the units disagree, and the decision is the maintainer's.

## Binaries

Each executable is a tarball per architecture, with its checksum beside it. Use a tarball when you manage the units yourself.

| Part | Value |
|---|---|
| Name | `sluis-<kind>-<name>_<version>_linux_<arch>.tar.gz`, for example `sluis-actor-store_2.0.0-alpha.1_linux_arm64.tar.gz`; the command-line tool is `sluis_<version>_linux_<arch>.tar.gz` |
| `<kind>-<name>` | The name of the [image](#oci-images) of the same executable: `actor-<name>`, or `driver-<owner>-<name>` |
| Contents | The executable, under the file name its build gives it, and `LICENSE` |
| Beside it | A `.sha256` file; all of them are listed in the release's `SHA256SUMS` |

The executables are static: Go with cgo off, Rust as musl through cargo-zigbuild. The card driver links `libpcsclite` and is built in a native job, so it is not in this list yet ([#860](https://github.com/truvity/sluis/issues/860)). A tarball does not yet place the executable at its install path; the packages do, and so do the images.

The build is `.goreleaser.yaml`, which `just release-gen` writes from the tree: an actor or driver that merges joins the release, and CI fails while the file differs. GoReleaser only builds (`just release-build`, which runs it with `--skip=publish` and no token); it pushes nothing. Rust executables are built under `cargo auditable` with the build machine's paths remapped, as Go is built with `-trimpath`, and `tools/release check-dist` fails on an executable that holds the workspace path, is not a static ELF of its architecture, or lacks the release version.

## Lambda zips

The zips are under `lambda/<version>/` for `arm64`, the default, and `x86_64`, named `sluis-<kind>-<name>_<version>_<arch>.zip` on R2 and in the GitHub release alike. A function is one zip per actor instance; its functions, schedules, roles and invoke grants are derived from the actor registry ([0013](/decisions/0013-release-train-packaging-and-distribution/#packaging-per-runtime)).

- `functions/`: one zip per executable; the handler is the package's binary, renamed `bootstrap`, behind the kit's invoke adapter. A work function carries no driver. Only `entry` has a listener and uses the Lambda Web Adapter, pinned and vendored.
- `layers/`: at most three sluis layers: the edge layer (with the vendored adapter, for `entry` only), the drivers layer and the configuration layer, so at least two of Lambda's five stay free for the operator.
- `extensions/`: the drivers of a holder's function. One Rust extension implements the AWS ports the holder needs: for store@ the AppConfig, SSM and DynamoDB ports, for key@ the KMS port.

What a layer or an extension bundles is in the [runtime dependency matrix](/distribution/dependencies/). An installation verifies the zips and publishes the layers into its own account; sluis publishes no public layer ARNs. The YubiKey driver, `sluis-node`, rqlite and every driver that needs a disk or a long-running process are not published for Lambda ([Serverless](/runtimes/serverless/)).

## OCI images

One image per process, so a container can run its one executable only. Multi-arch images are on GHCR as `ghcr.io/truvity/sluis/<kind>-<name>`, for example `ghcr.io/truvity/sluis/actor-entry`, from the first working version. No image is named `sluis`: that name belongs to v1. The tag is the release version, with no `latest`; pull by digest, and find every digest of a release in its `release-images.txt`.

- The base is distroless `static`, or distroless with glibc and a pinned `pcsc-lite` for a cgo executable. What an image installs, and what stays on the host (pcscd, the CCID driver, polkit), is in the [runtime dependency matrix](/distribution/dependencies/).
- The executable sits at the package's path, `/usr/libexec/sluis/actors/<name>` or `/usr/libexec/sluis/drivers/<owner>/<name>`, byte for byte, and a label names its source package. A release test compares the images' binaries with the packages' files by hash.
- One image set serves the local installation and Kubernetes.

| Image | Holds |
|---|---|
| `actor-<name>` | The actor's executable |
| `driver-<owner>-<name>` | The driver's executable |
| `vendor-rqlite` | `rqlited`, the engine of the rqlite store driver on the local installation, at `/usr/libexec/sluis/vendor/rqlited`, from the release archive that `just rqlite-fetch` checks against its SHA-256. It is on a distroless base with glibc and a busybox, because the engine has no command for its health check |

The card driver has no image yet ([Gaps](/distribution/dependencies/#gaps)). The command-line tool is a tarball only.

```sh
# Example
docker pull ghcr.io/truvity/sluis/actor-entry@sha256:<digest>
```

### How the images are built and tested

GoReleaser does not build the images. `tools/release publish-images` builds each one with `docker buildx` from the archive of the same run (the file `SHA256SUMS` lists) and pushes it under the release version, in the job that holds the credentials. `tools/gen/release` writes the list, `deploy/release/images.yaml`, and the Dockerfiles in `deploy/release/`: one `COPY` of one executable and an `ENTRYPOINT`, on the base that `deploy/local/Dockerfile` pins. Buildx adds no provenance or SBOM of its own to an image. Nothing about an image is signed ([Release signing](/distribution/release-signing/)).

`just release-rehearsal` runs both halves of a release, minus the GitHub release, and pushes to a registry that it starts on a free loopback port, with no credential. CI runs it when a change can affect the release (see [Releasing](#releasing)). Before the first push, `tools/release preflight` fails if any image already has the release version as a tag that this run did not push (see "Running the failed job again" for how a run knows): a tag is not pushed over, as far as a check followed by a push can promise it (best effort, because a registry has no conditional push; `check-images` verifies the result). After the push, `tools/release check-images` reads the registry and fails unless, for every image:

- the release version is a tag of the repository, no tag floats (a tag that is no release version, such as `latest`, fails), and on the throwaway registry the version is the only tag; earlier releases beside it on ghcr.io are expected;
- no repository is named `sluis`;
- the index holds `linux/amd64` and `linux/arm64` and nothing else, and its digest is the one in `digests.txt`;
- every manifest, config and layer, the base's included, is the bytes of its digest;
- the image is the pinned base plus the build: the index, the manifest and the configuration have no field the build does not set; the manifest holds exactly the layers of the base that the Dockerfile pins by digest (read from its registry by that digest, its manifest and configuration checked against their digests), in order, and then the layers the build added; the configuration is the base's (`Env`, `User`, `WorkingDir`, and any `Volumes`, `ExposedPorts`, `Healthcheck` or other field, which must equal the base's or be absent) with the entrypoint and the labels of the release added; `rootfs.diff_ids` are the base's followed by the hash of what each added layer unpacks to;
- the entrypoint is the install path, the user is the nonroot user of the base, and the labels name the image, the version, the commit and the source package;
- the layers the build added hold the files the list names and nothing else, none of them writable, and the executable is the file of the archive of the same architecture, hash for hash. The images are built from those archives in the same job, so this proves the round trip through the registry (no layer or tag was changed on the way), not that the archive is what the sources produce. For `vendor-rqlite`, the file `just rqlite-fetch` verified, and its image carries rqlite's MIT notice, `/usr/share/doc/sluis/vendor-rqlite/LICENSE`).

`tools/release release-images` writes `release-images.txt` from the digests: one line per image, `<repository>:<tag>@sha256:<digest>`. It and the SBOM of every image are added to `SHA256SUMS`, which without signing is the one anchor of trust of a release, and `tools/release check-sums` checks that every line names a file with that hash. The build's own `SHA256SUMS` may not list them: `check-dist` refuses a line for the audit catalogue, the list of images or an image SBOM before anything is pushed, and `check-dist -late` accepts them after `sums-add`.

The layers the build adds may hold regular files only; a link or a device in one fails the check. The `history` of the configuration is not compared, and the base is read from `gcr.io` over the network at release time (the Dockerfile's digest is the pin; nothing else of the base is committed).

The registry client sends its token only to an HTTPS token endpoint on the registry's host or on `ghcr.io`. It reads at most 1,000 tags of a repository.

### SBOMs

Each archive has an SPDX 2.3 JSON SBOM beside it, `<archive>.sbom.spdx.json`, and each image has one made from the registry by digest. syft makes them. It reads the Go modules from the build information of an executable and the Rust crates from the list that `cargo auditable` records in it (`tools/release/cargo-auditable.sh` is the tool GoReleaser's Rust builder runs). The documents of the archives and of the images are listed in `SHA256SUMS` with the archives.

`tools/release check-sboms` validates every document in the rehearsal: the fields SPDX 2.3 requires of a document and of each package, unique ids, relationships that name elements the document has, syft as the creator, and at least one crate (`pkg:cargo/`) in the SBOM of a Rust executable or one Go module (`pkg:golang/`) in that of a Go one, so a build that recorded nothing fails. It is a structural check of the format, not a run of the SPDX project's own validator.

## Releasing

A release is a tag `v2.<minor>.<patch>` or `v2.0.0-alpha.<n>` that the maintainer signs and pushes. Nothing else makes one: no workflow creates a tag, and a pull request never runs the release workflow. Nothing in the release is signed beyond the tag (decided 2026-11-07): the workflow has no `id-token` permission, makes no keyless signature and no provenance attestation, and `SHA256SUMS` is the trust anchor of the files and the digests ([Release signing](/distribution/release-signing/)).

Before the first tag, once:

- **ghcr.io.** The workflow's own token pushes the images, with `packages: write`. The first push creates one package per image, linked to this repository through the `org.opencontainers.image.source` label. Nothing in the workflow makes a package public. GitHub documents a new package as private by default and offers no API to change that afterwards (the REST API for packages lists, gets, deletes and restores), yet the 23 packages that the first alpha created came out public, as do all the other container packages of the organisation, which are pushed from public repositories the same way. That is observed behaviour, not a documented guarantee, so the release checks it: before the GitHub release leaves draft, the job pulls every image by its digest without a credential, fails for each package that is not public, names it with the page where its owner changes the visibility (`https://github.com/orgs/truvity/packages/container/package/sluis%2F<name>/settings`, then Danger Zone, Change visibility, Public), and leaves the release as a draft. The owner then makes those packages public and runs the failed job again (`gh run rerun <run id> --failed -R truvity/sluis`); see "Running the failed job again" below.
- **Immutable releases.** Turn on "Immutable releases" in the repository settings (Settings, General, Releases) so that a published release cannot change. `main` already protects its commits. The release job reads the setting before it changes anything, and it fails closed (owner decision, 2026-11-12): it stops when the setting is off, and it stops when it cannot read the setting. Reading it needs a token with the repository permission "Administration: read", which the token of a workflow does not have, so the job must be given such a token for a release to go ahead. The message of the failure names the setting and says this.
- **The tag rulesets on `v2.*`, applied by the owner.** `v2-tags-create` lets only the owner create a tag that matches `v2.*`, and `v2-tags-immutable` lets nobody update or delete one. Both exist. Without the first, anyone with write access to the repository could tag a branch whose copy of `release.yaml` has no gate: GitHub runs the workflow file of the tagged commit, so the gate lives in the file it protects and cannot stop that. What stops it is that only the owner can create the tag. There is no `environment: release` and no approval step, by the owner's decision.

For each release:

1. Rename `## Unreleased` in `CHANGELOG.md` to the version (`## 2.0.0-alpha.2`), in a pull request that merges to `main`. The push of that commit starts the release candidate ([The release candidate](#the-release-candidate)): wait for the run of `Checks` and the run of `Candidate` on `main` for that commit to finish green. A failure of either costs no version number: fix it on `main` and build it again as "The release candidate" says (a changed first `## ` heading line, or a re-run of the failed job). Also add the SHA-256 of the previous release's published `SHA256SUMS` to `deploy/verify/previous.sums` when a release becomes the previous one (`deploy/verify/previous.sh` says how). The text of the changelog section is the release's notes; a release with no such section fails.
2. Tag that commit and push the tag, one tag per push (GitHub starts no workflow for a push of more than three tags):

   ```sh
   # Example
   git tag -s v2.0.0-alpha.1 <commit on main>
   git push origin v2.0.0-alpha.1
   ```

3. The `Release` workflow runs two jobs in order, and builds nothing:
   - **gate.** It refuses a ref that is not a tag of the form `v2.<minor>.<patch>` or `v2.0.0-alpha.<n>`, a commit that is not an ancestor of `main`, one whose run of `Checks` on `main` is not a finished success ([REQ-SUPPLY-032](/requirements/supply/#REQ-SUPPLY-032)), and one without a green candidate: the newest run of `candidate.yaml` for that commit from a push to `main` must have succeeded and still hold its three artifacts, `release-dist`, `release-packages` and `evidence` ([REQ-SUPPLY-048](/requirements/supply/#REQ-SUPPLY-048)). It passes the id of that run on.
   - **release.** It has the write permissions and builds nothing, and no step of the tag run runs dependency build code (build scripts and macros of the Rust and Go dependencies). It still runs system tools: `setup-devbox` and the Nix packages it installs, `docker` and BuildKit, `gh`, `jq`, `syft` and the Go compiler for `tools/release`, whose only third-party module is `go.yaml.in/yaml/v3`. It downloads the candidate's three artifacts from the run the gate found, checks that the download changed no tracked file of the tree (`git diff --quiet HEAD`; the tree is a trust anchor of the catalogue check and of the plan of the packages), and trusts none of the files except by hash. `check-dist -exact` refuses anything in the download that is not a regular file of the release and checks the archives against the configuration; `metadata.json` must name the tag's commit in full and a release version. `check-catalogue` checks the audit catalogue that the candidate's build made against the tagged tree ([The audit catalogue](#the-audit-catalogue-of-a-release)). `check-candidate` holds every file it will publish to the candidate's evidence: the files of the release directory, the packages and their sums are exactly the files whose digests the evidence names, the evidence is about this tag's version and commit, and every suite of the install tier passed on every system and both architectures (a refusal of the upgrade or the downgrade with a named reason passes, a failure does not). `check-packages` holds the packages to the plan of the tagged tree. Only then does it refuse a tag that already has a public release, push the images that are not at this version yet (an image that is there is kept only if an earlier attempt of this same run pushed it, and refused otherwise), run the release test of the images against ghcr.io, make the image SBOMs, copy the packages' sums and the evidence into the release directory and add them, the list of images, the audit catalogue and the SBOMs to `SHA256SUMS`, bring the GitHub draft to hold exactly the files of the release (the archives, checksums and SBOMs, `SHA256SUMS`, `SHA256SUMS.packages`, `evidence.json`, `release-images.txt`, the image SBOMs, the audit catalogue, and every `.deb` and `.rpm`), pull every image by its digest with no credential ([REQ-SUPPLY-046](/requirements/supply/#REQ-SUPPLY-046)), and only then make the release public (a pre-release for an alpha). The anonymous pull asks for the manifests and, with a `HEAD` request that follows the redirect to where the registry keeps blobs, for the configuration and every layer of each; it does not download the layers (`check-images` has read and hashed them).
4. Check the result: the release holds the archives, `SHA256SUMS`, a `.sha256` and an SPDX SBOM for each archive, `release-images.txt`, an SBOM for each image, `audit-catalogue.yaml`, the `.deb` and `.rpm` packages with `SHA256SUMS.packages`, and `evidence.json`. `SHA256SUMS` lists the last two as well as everything else it lists, so from it a reader reaches every package and the report that says they were installed.

### The release candidate

A release publishes the bytes of a **candidate** (owner decisions of 2026-11-09: D5 promote, D10 evidence as a release asset). `candidate.yaml` builds them once, installs them as packages, and keeps them; the tag run builds nothing. So the bytes that were installed are the bytes that ship, and a failure of the install costs no version number: nothing is tagged until the workflow has passed on the commit ([REQ-SUPPLY-048](/requirements/supply/#REQ-SUPPLY-048)).

- **When it runs.** On a push to `main` that changes the **first `## ` heading line** of `CHANGELOG.md` to a release version that has no tag (`tools/release/candidate-scope.sh`; a push of several commits is compared as a whole), with that version. Nothing else in the file starts it: a commit that edits the notes below the heading does nothing. It cannot be started by hand: GitHub lists a manual workflow only from the default branch, which is not `main` yet.
- **Building it again.** Two ways, and the tag is always the commit of the run that passed. (1) A failed install job of a candidate is run again with `gh run rerun <run id> --failed`: its evidence is uploaded under the name of its attempt (`install-evidence-<arch>-<attempt>`), so the second attempt does not collide with the first, and the job `candidate` takes the newest attempt of each architecture that its own run has reached (`tools/release/candidate-evidence.sh`); the tag is that run's commit. (2) Anything else (a failed build, a cancelled run, an expired candidate, a fix on `main`) needs a **new commit that changes the first `## ` heading line**, for example by appending a date: `## 2.0.0-alpha.2 - 2026-11-12`; the notes below it still belong to the release. The tag is then that new commit.
- **What it does.** The job `build` runs GoReleaser with `GORELEASER_CURRENT_TAG=v<version>` (no tag exists yet, and no restored cache), builds the packages and those of the previous release, and uploads `release-dist` (the archives, their checksums and SBOMs, `SHA256SUMS`, `metadata.json`, the audit catalogue), `release-packages` (the `.deb` and `.rpm` files and their `SHA256SUMS`) and the inputs of the install tier. The job `install` runs the install tier on an amd64 and an arm64 hosted runner, three systems on each. The job `candidate` joins the two reports (`tools/verify evidence-merge`: the same version, commit, packages and previous release in both, one run for each architecture), adds the digest of every file of the release directory, requires every blocking suite to have passed on every system of `nodes.tsv`, and uploads `evidence.json`. Then it holds the downloaded files to that evidence with the very check the tag run uses, and breaks them on purpose (`tools/release/candidate-mutants.sh`): one byte of an archive, of the release's `SHA256SUMS`, of a `.deb`, of an `.rpm`, of the packages' sums and of the evidence, a file added to the release or to the packages, a file taken from either, another commit and another version must each be refused.
- **How long it is kept.** 30 days (the artifacts `release-dist`, `release-packages`, `evidence` and the tier's inputs). The owner tags after reviewing, which can take days, and an expired candidate makes the gate refuse the tag with a message that says so. A rehearsal keeps its artifacts for a day.
- **The rehearsal.** `checks.yaml` calls the same workflow (`rehearsal: true`) on every pull request and merge group that can affect the packaging, the units, the install tier, the release tools or the workflows, and on every push to `main`, with the next alpha after the latest tag. So the build, the packages, both architectures of the install tier, the joined evidence, the gate and its mutations run on the pull request that changes them, and the one name to require, `Checks`, needs the result. What a pull request cannot run is the part that needs a tag: the gate's lookup of the candidate's run, the download of its artifacts from another run, the attachment of the files to the GitHub release, and the draft. Those are covered by stand-ins and fixtures only, and the first real tag is their first real use.
- **What the evidence is.** The report names every package file by digest and every file of the release directory by digest, with the result of every suite on every system and architecture (`deploy/verify/evidence.schema.json`). It is a defect gate, not a supply-chain control: the jobs that run the packages could write a false report if a dependency were malicious, as the build could write a false archive. The split bounds what a compromised dependency can reach (every candidate job holds `contents: read` and nothing else, no token, no `id-token`, and runs on GitHub-hosted runners only), and the tag run trusts none of the files except by hash. With nothing signed (decided 2026-11-07), nothing stronger exists. **Residual risk, the runtime token.** Every step of a job holds that job's `ACTIONS_RUNTIME_TOKEN` and can use the artifact service with it until the job ends. So the job `build`, which runs dependency build code, can create any artifact name of the candidate's run (`install-evidence-amd64-1`, or `evidence` before the job `candidate` writes it), and the job `candidate` writes its artifacts with `overwrite: true` to replace such a name by the real file; the joiner takes only attempts its own run has reached. None of this changes the trust: the build job writes the archives and the packages themselves, and the evidence is checked against their digests, so a forged report is as good as a forged build, which is the defect-gate limit above. In the tag run the same token is in every step of the job `release`, none of which runs dependency build code; the claim there is "no dependency build code", not "no third-party code" (the Nix tools of `setup-devbox`, `docker`, `syft` and BuildKit run), and the record of the pushes relies on it. A board run is advisory for an alpha (owner decision D6): its report may be attached to the release by hand later, and it is not part of the gate.
- **Where the files go.** The packages are attached to the GitHub release with their sums as `SHA256SUMS.packages`, and the evidence as `evidence.json`; `SHA256SUMS` lists both. The apt and dnf site stays in v1 parity (owner decision D1). A package file name uses the version as tagged (`sluis-key_2.0.0-alpha.2_amd64.deb`, not the `~` that the package manager writes inside the package).

### The audit catalogue of a release

The emitters of a release put its version in every audit record (`metadata.product.version`). The writer validates a record against the `AuditCatalogue` config document and refuses a record whose release is newer than the catalogue's, so that record is quarantined, not logged ([REQ-AUDIT-146](/requirements/audit/#REQ-AUDIT-146), [0030](/decisions/0030-audit-records-and-the-usage-stream/)). An installation that runs a release without that release's catalogue loses the audit records of its own services. The catalogue is therefore a part of the release.

- **What the release ships.** `audit-catalogue.yaml`, the document of the release: the action table of the tagged commit with the JSON Schema of every action's records, as the one item `default`, with `release` set to the version (the tag without the `v`). The build job makes it with `go run ./tools/gen/audit -catalogue audit-catalogue.yaml -release <version>` (its generator compiles third-party Go modules, which the job that holds the tokens must not run). The release job does not trust the file: before it pushes anything, `tools/release check-catalogue` stops the release unless the file is the catalogue of the local installation (`tests/installations/local/config/audit-catalogue.yaml`, which `just audit-check` holds equal to the generator's output on the commit the gate found green) with only the release replaced: the same policy version, the same actions and the same schemas byte for byte, and also the actions of the action table and the committed schemas (`kits/conformance/audit/schema`) as JSON. It reads the file as strictly as the writer does, with `yaml/v3` alone: one document, no alias, anchor, explicit tag or merge key, no field the item does not declare, a policy version, and schemas that are plain JSON (a duplicate key or a number that is not what it says fails). A file the build altered, or one made for another tree, fails there before anything is pushed, not as an audit outage after the operator publishes it. No empty action name passes. It is a release file, listed in `SHA256SUMS`. It is not signed: the release holds no key.
- **What the operator does with it.** Take `audit-catalogue.yaml` from the release and check it against `SHA256SUMS`. Put it in the config sources as the `AuditCatalogue` document, sign it with the publisher key like any config document (a `seq` above the last one), and publish it to the config source. store@ loads it with the next snapshot.
- **The order of an upgrade.** Publish the catalogue first. Then restart the writer, because it reads the catalogue only when it starts. Then roll the emitters to the new release. The other way round, the new emitters' records are refused until the writer restarts. The table only grows within a major version, so the catalogue of the newest release also holds for the records of every older one ([0030](/decisions/0030-audit-records-and-the-usage-stream/)).
- **The local installation from the published images.** The catalogue of a checkout names release `0.0.0`, so with `SLUIS_LOCAL_IMAGES=release` the harness signs the release's `audit-catalogue.yaml` instead (`SLUIS_RELEASE_CATALOGUE`, a file or an `https` URL), and refuses one that is not for the version of the images that run: the tag the pinned images carry, which must agree with `SLUIS_LOCAL_VERSION` if that is set too ([Local](/runtimes/local/#images)). The rehearsal does this on every run that touches the release, so its smokes, which read the audit trail, fail if the catalogue is missing or wrong.

**What a failure leaves.** Before the tag, a failure of the candidate leaves nothing and costs no version number. After it, the order of the release job is: hold the files to the candidate's evidence, check, push the images that are missing (recording each digest the moment it is pushed), check them, bring the draft to hold the files, pull the images anonymously, make the release public. A failure before the push leaves nothing. A failure after it leaves the images on ghcr.io, and a failure from the draft on leaves a draft as well. Nothing is announced. A tag is not pushed over, as far as a check followed by a push can promise it: the registry has no conditional push, so a push by someone else between the check and the push of this job is possible, and `check-images` then fails the release because the content is not the build's (best effort, not a guarantee).

**Running the failed job again** ([REQ-SUPPLY-037](/requirements/supply/#REQ-SUPPLY-037)). Run `gh run rerun <run id> --failed -R truvity/sluis`. It runs the `release` job again with the same candidate, downloaded again from the run the gate found, so nothing is rebuilt and the same bytes are held to the same evidence. The job is two stages of one recipe (`just release-publish push`, then `finish`) with a step between them that uploads `dist/pushed.txt` as the artifact `pushed-digests-<attempt>` of the run, whether the push passed or not. `publish-images` appends the digest of an image to that file as soon as the image is pushed. A later attempt downloads the artifacts of the attempts before it and keeps an image that is in the registry **only if its digest is the one recorded**: the artifact belongs to the run and only a job of this run can write it, so a tag that someone with the right to push packages put there is not kept. No step of the tag run runs dependency build code (the candidate's build did, in the candidate's run), so the one job that writes a record is this one, after this check, short of the runtime-token residual below; the release job refuses, before it pushes anything, an artifact named `pushed-digests-<n>` for its own attempt or a later one, and any other name that starts with `pushed-digests`. The upload also fails, and does not overwrite, if the name is already taken. Such a tag, one nobody recorded, or a recorded one whose digest has changed, fails the job before the first push, naming it, and that version is not used again. `check-images` then verifies every image, kept or pushed, against the archives of the candidate and the pinned base.

The draft is kept and brought to the files of the release, by its id. The job lists the releases of the tag again just before it changes anything and refuses if any of them is public; it reads a draft by its id once more before it touches it, and touches it by that id (never by its tag, which would resolve to a release the owner published in the meantime). Several drafts of the tag are deleted, each by its id, and one is made. Then the tag must name exactly one release, a draft, whose id is read once, and its assets are compared with the files by name, size and the digest the API gives (`tools/release assets-plan`): an asset that is there complete is kept, so **a re-run uploads only what is missing**; one that is unfinished, of another size or digest, or no file of the release is deleted by its asset id and, if it is a file, uploaded again; three rounds, because an upload can fail half way; and an empty plan afterwards is the check that the draft holds the release and nothing more. The id comes from listing the releases right after the create, not from the response of the create call (`gh release create` prints a URL and `gh api -X POST` would also create a tag that is missing, which this job must never do); if the listing lags behind the create, the job fails closed with the draft in place, and running it again continues with it. The change to public is made by the id, after the releases of the tag have been listed once more and said the same thing. The delete of an asset or of a draft is not conditional (the API has no "delete if still a draft"), so a window of the length of one request remains between the last read of a draft and the delete, in which the owner could publish it by hand; it is a few milliseconds, and the check before it is what makes it that short, not a guarantee. So a run that stopped because a package was not public is finished by making the package public and running the failed job again. What it does not cover: a push step that is killed (a cancelled run, a runner that dies) after an image was pushed and before the artifact was uploaded leaves a tag that no record names, and the re-run refuses it; an expired candidate (it is kept for 30 days) is built again by a new commit that changes the first `## ` heading line of `CHANGELOG.md`; and if the cause is in the code and not in a package or the draft, the next attempt is the next version (`v2.0.0-alpha.3`), because the tag cannot be moved. How much of the idempotent publish the workflow gives: images, and the release's files. The chart is not built yet, so REQ-SUPPLY-037 stays partial.

**What a pull request runs.** `Checks` has a job, `release`, that runs `just release-rehearsal` (the two halves above against a throwaway registry, then the local installation from those images with both smokes). It takes about 30 minutes with a warm cache, so a pull request or a merge group runs its steps only when a changed file is on a list of the release machinery and its build inputs: the GoReleaser configuration, the packaging files, `Justfile`, `devbox`, the manifests, modules and lock files, the toolchain, the version stamp, `deploy/release`, `deploy/vendor`, `deploy/local`, `tools/release`, the local installation and the smokes, the two workflows, and the policy schema page that an actor embeds. The code of an actor or a driver is not on the list. That is a bet, not a proof: the job `arm64` builds every executable with the same toolchain and `code` and `smokes` test it, but they build the Rust workspace in one run, so Cargo unifies features across packages, and the release builds each package alone, with `cargo auditable` and remapped paths. A change that compiles only because a sibling enables a feature would pass them. The last step of the job `code` runs `just rust-check-isolated`, which checks each Rust package the change can affect alone (about 10 to 20 seconds each when warm, about a minute if every package is affected by a change to `Cargo.lock` or a kit); what it cannot catch shows first on the push to `main`, which always runs the full job, and the gate refuses that commit. A push to `main` always runs the job in full, and the gate above requires that run.

The workflow has an empty permission block at its top, and only its `release` job can write ([REQ-SUPPLY-033](/requirements/supply/#REQ-SUPPLY-033), [REQ-SUPPLY-041](/requirements/supply/#REQ-SUPPLY-041)); its checkouts keep no credential ([REQ-SUPPLY-042](/requirements/supply/#REQ-SUPPLY-042)); and no cache is restored, so a release builds from the sources and the locked dependencies alone. Tests over the workflow files hold those rules.

## GitHub Releases

GitHub Releases is the immutable record. Each release holds the same files as the R2 version directory. If a file on R2 and a file on the release differ, the release is right.

## Compatibility

The artifacts of one release are built, tested and shipped together, and each also works with those of the previous release of the same major version, so a rolling deployment can run two neighbouring releases at once and a rollback needs no migration ([0015](/decisions/0015-evolution-and-compatibility/#n-and-n-1-inside-a-major-version)). Between releases, compatibility follows semantic versioning ([0013](/decisions/0013-release-train-packaging-and-distribution/#compatibility-between-releases), [#1715](https://github.com/truvity/sluis/issues/1715)).
