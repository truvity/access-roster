The roadmap lives in the `Product milestone` field of the public [sluis v2 board](https://github.com/orgs/truvity/projects/9), and the [project status](/status/) page shows how far each milestone has got. This page says what each milestone is for and when it is done; the reasoning for the order is in [ADR 0011](/decisions/0011-runtimes-and-installations/#delivery-order).

v1 keeps its own roadmap on the [sluis v1 board](https://github.com/orgs/truvity/projects/10), on `master`. New feature requests target v2 ([ADR 0001](/decisions/0001-v1-and-v2-lines/)).

## Where v2 stands

As of 2026-11-04, the first working version is being built, and the design is still ahead of the code. What exists are the [decision records](/decisions/), the [requirements](/requirements/), the design pages, and the part of the code listed in [What runs today](#what-runs-today). Root custody lives in [ritueel](https://ritueel.id), a separate project also in design. The test harness certifies its intermediates with any certificate authority that signs a PKCS#10 request; ritueel's software-root mode is the certifier the CI runs when it exists ([#1071](https://github.com/truvity/sluis/issues/1071)).

## What runs today

Measured on 2026-11-04. Each line is a proof you can run; the commands are `devbox run -- just <recipe>`, and the recipes are described on [The local installation](/runtimes/local/#recipes) and on [Bare metal](/runtimes/bare-metal/#deploy-and-prove-on-three-boards).

| Milestone | State | Demo |
|---|---|---|
| **M1, the spine** | Passes on the local installation: a client asks `policy` for a decision and `signer` for a token, the token verifies against the key set that `entry` serves, the records of the run are in the audit log, and `sluis audit verify` checks the log | `local-up`, then `local-smoke` |
| **M3, the boards** | Passes on three boards over one shared three-node rqlite cluster: the same spine runs against each board in turn, and from the second board on it finds the earlier boards' signing key, which shows the shared store | `build-arm64`, `boards-deploy`, then `boards-smoke`; `boards-undeploy` removes it again |
| **M2, the person** | Passes on the local installation: `session` seals the facts of a session chain under the tenant's `chain` key, and `session` and `exchange` alone open them ([0006](/decisions/0006-keys-and-sealing/#data-keys)); `sluis login` signs a person in through the upstream identity provider, and `sluis token` exchanges the token for an audience (RFC 8693) | `local-up`, then `local-person-smoke` |

The deny matrix of the local installation also runs (`local-deny`): every caller against every socket, at the socket and at the guard. CI runs the deny matrix and the two smokes of the local installation, M1 and M2, on every pull request.

## A core and two later modules

v2 has a core and two later layers. The core is workforce single sign-on and the reconcilers: milestones 1 and 2 below. The CIAM layer ([0032](/decisions/0032-customer-identity-installations/)) and the quota module are the later layers, each packaged so that an installation runs it only if it needs it.

An installation is one of two kinds, and the two are distinct installations of the same product, each with its own boundary, keys and state:

- A **workforce installation** signs in the people of an organisation (its employees) and reconciles its systems. It runs the foundation, the identity module and the audit module.
- A **customer installation** adds the CIAM layer ([0032](/decisions/0032-customer-identity-installations/)) and brokers an external customer-identity product for the end users of several products. The core is the same in both.

An installation may also run the foundation with the audit module only, to keep the audit trail of a product that does not use sluis for sign-in ([Audit](/concepts/audit/#audit-alone)). The foundation (store@, exporter@ and key@) and the modules are explained on [Families](/concepts/families/#the-foundation-and-the-modules).

Each [decision record](/decisions/) of the later modules says which module it belongs to on its `Layer` line ([the format](https://github.com/truvity/sluis/blob/main/docs/decisions/README.md#format)), and the [decision index](/decisions/) shows it, and the [runtimes](/runtimes/) page lists the tested installations.

## Core

The core is delivered in two product milestones, in this priority order.

1. **First working version.** The local installation, plus the foundations every installation stands on. The local installation is Docker Compose on a workstation: one container per actor and per driver, built from the published images ([#1123](https://github.com/truvity/sluis/issues/1123)), with the minimal drivers (rqlite with one node as the store's engine, a SQLite audit index, a files blob, a spool or direct transport), software keys by default, sign-in through the generic OpenID Connect upstream tested against a real identity provider ([#1106](https://github.com/truvity/sluis/issues/1106)), and the audit log with Search ([#1120](https://github.com/truvity/sluis/issues/1120), [#1121](https://github.com/truvity/sluis/issues/1121), [#1122](https://github.com/truvity/sluis/issues/1122); [The local installation](/decisions/0011-runtimes-and-installations/#the-local-installation)).
   - **The core actors** are `entry`, `session`, `exchange`, `signer`, `policy` and `ca`, on the foundation of store@, exporter@ and key@. `ca` is a small v0 that issues the token certificate under the node's intermediate; its other profiles are v1 parity. The `console`, with the operator API behind it and its pages, is v1 parity too, so the first version has only the browser flows that sign-in and passkeys need. The actors serve the basic OpenID Connect flow (discovery and the key set, authorization with PKCE, tokens, refresh, UserInfo and revocation, form post), and passkeys and step-up ([#885](https://github.com/truvity/sluis/issues/885)).
   - **The boards' hardware base** is part of this milestone: the YubiKey PIV key driver on the cards, the PIN released from slot 87 to a locked `key@` (with, still in this milestone, the card driver checking the `KeyPlan`'s signature and the peer's slot 87 signature itself before it seals or opens, so that a compromised `key@` can no longer read the PIN), the mainline Ubuntu 26.04 and Rocky 10 images on the boards, and the three-node rqlite cluster that the boards run (the PIN release relies on it) ([Bare metal](/runtimes/bare-metal/)).
   - **Root custody** reaches the installation through the hand-off to ritueel's software-root mode ([#1066](https://github.com/truvity/sluis/issues/1066), [#1071](https://github.com/truvity/sluis/issues/1071)).
   - **The foundations** are the build and release train, the contracts and the two registries (kinds and actors), the store with its drivers and signed configuration, and key custody.
   - **exporter@ is in this milestone,** with the directory driver, the static key set and its publication report ([#1453](https://github.com/truvity/sluis/issues/1453)), then the bucket driver and the edge purge for the boards ([#1454](https://github.com/truvity/sluis/issues/1454), with a static, narrow R2 token until [#817](https://github.com/truvity/sluis/issues/817) mints one in v1 parity), so that a revoked key leaves the published key set ([#962](https://github.com/truvity/sluis/issues/962), [#1338](https://github.com/truvity/sluis/issues/1338)) and `sluis key revoke` can confirm it ([#1362](https://github.com/truvity/sluis/issues/1362), [0009](/decisions/0009-export/#publishing-public-material)). The other destinations, the other exportable kinds and the Lambda trigger come at v1 parity ([#1714](https://github.com/truvity/sluis/issues/1714)).
   - **The milestone also holds** the published images with checksums and SBOMs, and no signature ([ADR 0013](/decisions/0013-release-train-packaging-and-distribution/#signing-and-checksums), [#1124](https://github.com/truvity/sluis/issues/1124)), and the conformance pipeline against the local installation ([#1100](https://github.com/truvity/sluis/issues/1100)). The maintainer still signs each tag by hand.
   - **Moved out on 2026-11-07,** by the maintainer's scope decisions, because the done-when below needs none of them:
     - *To v1 parity:* workload identity ([#870](https://github.com/truvity/sluis/issues/870)), federation ([#963](https://github.com/truvity/sluis/issues/963), [#964](https://github.com/truvity/sluis/issues/964)), the proof verifiers ([#965](https://github.com/truvity/sluis/issues/965)), the signing API ([#890](https://github.com/truvity/sluis/issues/890), [#1117](https://github.com/truvity/sluis/issues/1117)), the distribution site ([#873](https://github.com/truvity/sluis/issues/873)), the console, and `ca` beyond the token certificate ([#913](https://github.com/truvity/sluis/issues/913)). Passkeys and step-up stay. `sluis config check --live` and `sluis config explain --live` go too, because they read through the console API. Nine rows with no consumer in the first version go with them: REQ-ISO-036, REQ-ISO-032, the queue clause of REQ-ISO-024 (now REQ-ISO-119), REQ-POLICY-016, REQ-KEYS-063, REQ-DATA-110, REQ-DATA-065, REQ-AUDIT-174, REQ-AUDIT-177 and REQ-AUDIT-149. Three rows of `sluis config check` go too, because no flag names a second boundary and no config file names the driver of key@ or of an audit piece: REQ-ISO-118, REQ-DATA-107 and REQ-KEYS-015.
     - *The boards' rqlite* has no TLS and listens on the board address behind a firewall, which is a known limit of the test installation: REQ-DEPLOY-004 and REQ-DATA-074 are v1 parity. Before any real PIN or real data goes on a board, the maintainer closes or accepts each known limit in writing ([REQ-DEPLOY-047](/requirements/deploy/#REQ-DEPLOY-047), [#1584](https://github.com/truvity/sluis/issues/1584)).
     - *To Backlog:* the signing of release artifacts, keyless and OpenPGP, with the staff key and GPG work ([Later](#later)).
   - **Done when** the example bootstrap file for local starts under Docker Compose from the published images, the integration tests run against it in CI, and the three boards run the same spine with a YubiKey as the key driver. Every command in the [first-version command table](/reference/cli/#the-first-working-versions-commands) exists, and each has a test in CI against the local installation; card commands are attested from a board run.
2. **v1 parity.** Everything v1 does, and the capabilities v2 adds beside it. This is where the reconcilers, run-time tenant settings and the console write path, back-channel logout, and agent sessions with credential minters and exchange grants are delivered. It also holds what moved out of the first version on 2026-11-07 (see above). Parity means that the workloads that use v1 today can be wired to the new sluis, possibly in a different way or with a different configuration, not that behaviour is identical. The milestone has two gates ([ADR 0015](/decisions/0015-evolution-and-compatibility/#the-v1-parity-milestone-has-two-gates)):
   - **v1-retirement gate.** The replacements of what v1 does. **Done when** every row of the [v1 parity checklist](/features/) is `Done` or `Changed` (with its decision), the Lambda and Kubernetes installations are built and tested ([installations](/runtimes/)), the inventory of v1's relying parties is complete, and v1's audit and billing history is handled ([ADR 0015](/decisions/0015-evolution-and-compatibility/#v1s-history)). v1 is retired when this gate holds and the fact of [ADR 0001](/decisions/0001-v1-and-v2-lines/) holds.
   - **New-capabilities gate.** What v1 never did: the SSH CA, database certificates, host enrolment, trust sync, the cert-manager issuer, the peer witness, the reconcilers and the rest of the boards installation. **Done when** each is built and tested; the installation that needs it delivers it, and it does not hold v1 back.

## Later layers

The later layers are delivered in two more product milestones, after the core and in this order. The core does not wait for them, and a workforce installation does not carry them.

3. **CIAM upstream.** Group single sign-on: the end users of several products of one group sign in once across all of them. sluis stays a broker and hosts no customer accounts: the customer-identity product is one more OpenID Connect upstream ([OIDC upstream](/integrations/oidc-upstream/), [ADR 0031](/decisions/0031-ciam-is-a-broker/)).
   - **Done when** the generic OIDC upstream ([#916](https://github.com/truvity/sluis/issues/916)) does claim mapping per upstream, `acr` and `amr` passthrough, step-up (RFC 9470) by re-authentication at the upstream, end-user subjects with their lifecycle ([#1717](https://github.com/truvity/sluis/issues/1717)), rate limits per connection, and the FAPI 2.0 Security Profile is served to clients that declare it ([#912](https://github.com/truvity/sluis/issues/912), [#929](https://github.com/truvity/sluis/issues/929)). Back-channel logout, inbound and outbound, is part of v1 parity, not of this milestone. The capacity of the Kubernetes installation is measured before any figure is promised ([ADR 0037](/decisions/0037-capacity-is-measured-before-it-is-promised/), [#1713](https://github.com/truvity/sluis/issues/1713)).
4. **Quota.** `quota` holds an allowance per tenant that the product pushes. It counts the allowance down as work is admitted, refuses at zero, and records every admit, refusal and push as an audit fact. Its metering events go to a usage log of their own, apart from the audit log. Plans, prices and money stay in the product ([ADR 0039](/decisions/0039-quota-allowance/)).
   - **Done when** a push sets or adds to an allowance idempotently, a request counts once however often it is retried, the admitted total never exceeds the allowance under concurrent requests, pushes included, and the usage log and the metering events are written (work item [#915](https://github.com/truvity/sluis/issues/915)).

## Delivery order

The tested [installations](/runtimes/) are built in this order:

1. **local first,** with the foundations (milestone 1). The boards' hardware base (the YubiKey key driver, the PIN release, the mainline images and the three-node rqlite cluster) is also part of milestone 1.
2. **Then boards, lambda and kubernetes, built and tested in parallel.** They start when the first working version is done, and none waits for another. For the boards this is the rest of the installation, such as the peer witnesses.
   - **boards.** Three single-board computers behind a Cloudflare tunnel, a YubiKey in each node, the store and the audit index on rqlite, and audit logs on R2 with the other nodes as peer witnesses ([Bare metal](/runtimes/bare-metal/)).
   - **lambda.** AWS Lambda.
   - **kubernetes.** The one tested Kubernetes installation ([Kubernetes](/decisions/0011-runtimes-and-installations/#kubernetes)).

EC2 is a possible bare-metal installation, not a delivery target, and not tested. Other installations are possible and untested. The order is reviewed when each installation ships, and ADR 0011 records any change.

## Later

Work planned after the parity milestone is marked Later on the board. It includes CIBA, in poll mode with a passkey on the approving device, once a real consumer exists ([#980](https://github.com/truvity/sluis/issues/980)); ACME for host certificates ([#978](https://github.com/truvity/sluis/issues/978)); device login ([#855](https://github.com/truvity/sluis/issues/855)); a FIPS build variant when a customer needs one ([#868](https://github.com/truvity/sluis/issues/868)); and other clouds and stores. Garage as the boards' blob store is backlog, because it ignores conditional writes ([#982](https://github.com/truvity/sluis/issues/982)).

**Staff keys** are in Backlog too: card binding per employee, the company's own OpenPGP keys for its staff (certified by sluis, listed in a staff keyring, and synced to staff GitHub accounts), and the same binding for a customer's JWK ([ADR 0043](/decisions/0043-a-person-binds-their-own-keys-to-their-identity-in-sluis/), [ADR 0042](/decisions/0042-sluis-syncs-company-issued-openpgp-keys-to-staff-github-accounts/), [#1719](https://github.com/truvity/sluis/issues/1719), [#1718](https://github.com/truvity/sluis/issues/1718), [#1076](https://github.com/truvity/sluis/issues/1076)). The maintainer decided on 2026-11-07 to move "card binding per employee and GPG key management" out of the first working version, v1 parity and CIAM upstream, and to keep it in Backlog. It is not scheduled, it is not a milestone, and none of the four milestones waits for it. The design is accepted and does not change. What it needs first: the hardware-attested sign-in of v1 parity, the directory and `adapter-github` of v1 parity, and, for customers, the customer upstream sign-in of CIAM upstream; before the build, the measurements against GitHub and the conformance test on a real card that the two records list under Follow-ups. The OpenPGP subkeys of the boards' nodes and the passkey sign-in tiers are not part of it and stay where they are.

**Signing of release artifacts** is in Backlog as well. The maintainer decided on 2026-11-07 that neither the keyless signing (cosign signatures, build-provenance and SBOM attestations) nor the OpenPGP signing of releases belongs to the first working version or to v1 parity. A release carries checksums and SBOMs, and the maintainer signs each tag by hand. The requirements REQ-SUPPLY-001, 002, 007, 008, 017, 018 and 043 are in Backlog, and the work waits with the staff key and GPG work ([ADR 0013](/decisions/0013-release-train-packaging-and-distribution/#signing-and-checksums), [#874](https://github.com/truvity/sluis/issues/874), [#1013](https://github.com/truvity/sluis/issues/1013), [#1074](https://github.com/truvity/sluis/issues/1074)). The signing API ([#890](https://github.com/truvity/sluis/issues/890)) is a separate thing and is in v1 parity.
