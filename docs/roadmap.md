The roadmap lives in the `Product milestone` field of the public [sluis v2 board](https://github.com/orgs/truvity/projects/9), and the [project status](/status/) page shows how far each milestone has got. This page says what each phase is for and when it is done; the reasoning is in [ADR 0044](/decisions/0044-sluis-v2-is-a-core-building-blocks-and-add-ons/) and, for the order of installations, [ADR 0011](/decisions/0011-runtimes-and-installations/#delivery-order).

v1 keeps its own roadmap on the [sluis v1 board](https://github.com/orgs/truvity/projects/10), on `master`. New feature requests target v2 ([ADR 0001](/decisions/0001-v1-and-v2-lines/)).

## Where v2 stands

As of 2026-11-12, the first working version (P1, the core) is being built, and `v2.0.0-alpha.1` was tagged on 2026-11-08. The design is still ahead of the code in the add-ons and the later blocks. What exists are the [decision records](/decisions/), the [requirements](/requirements/), the design pages, and the part of the code listed in [What runs today](#what-runs-today). Root custody lives in [ritueel](https://ritueel.id), a separate project that owns the roots, the root list, the CA bundle, the revocation lists, the keyring, what it knows about its cards, and the SSH CA. The test harness certifies its intermediates with any certificate authority that signs a PKCS#10 request; ritueel's software-root mode is the certifier the CI runs when it exists ([#1071](https://github.com/truvity/sluis/issues/1071)).

## What runs today

Measured on 2026-11-04. Each line is a proof you can run; the commands are `devbox run -- just <recipe>`, and the recipes are described on [The local installation](/runtimes/local/#recipes) and on [Bare metal](/runtimes/bare-metal/#deploy-and-prove-on-three-boards).

| Milestone | State | Demo |
|---|---|---|
| **M1, the spine** | Passes on the local installation: a client asks `policy` for a decision and `signer` for a token, the token verifies against the key set that `entry` serves, the records of the run are in the audit log, and `sluis audit verify` checks the log | `local-up`, then `local-smoke` |
| **M3, the boards** | Passes on three boards over one shared three-node rqlite cluster: the same spine runs against each board in turn, and from the second board on it finds the earlier boards' signing key, which shows the shared store | `build-arm64`, `boards-deploy`, then `boards-smoke`; `boards-undeploy` removes it again |
| **M2, the person** | Passes on the local installation: `session` seals the facts of a session chain under the tenant's `chain` key, and `session` and `exchange` alone open them ([0006](/decisions/0006-keys-and-sealing/#data-keys)); `sluis login` signs a person in through the upstream identity provider, and `sluis token` exchanges the token for an audience (RFC 8693) | `local-up`, then `local-person-smoke` |

The deny matrix of the local installation also runs (`local-deny`): every caller against every socket, at the socket and at the guard. CI runs the deny matrix and the two smokes of the local installation, M1 and M2, on every pull request.

## A core, building blocks and add-ons

On 2026-11-12 the maintainer re-planned v2. It is no longer a core with two later layers (CIAM and quota). It is a core, a few building blocks and optional add-ons, delivered in the phases below ([ADR 0044](/decisions/0044-sluis-v2-is-a-core-building-blocks-and-add-ons/)).

- **The core** is what every installation needs: install and run, the commands of the [first-version command table](/reference/cli/#the-first-working-versions-commands), `session`, `exchange`, `signer`, `entry`, and `ca` as a small v0 that issues the token certificate. The core installs and runs without any add-on.
- **The building blocks** are modules that a product may reuse beyond sluis, each behind an interface:
  - **store:** the generic store with its drivers ([0005](/decisions/0005-the-store/)). The driver holds bytes; the kinds are compiled in today. The rule until the blocks are extracted is that no domain type is coupled into a driver; new storage needs are kinds.
  - **key:** key custody ([0006](/decisions/0006-keys-and-sealing/)). It holds no root. ritueel owns the roots; sluis owns the intermediates and the request and install side ([0024](/decisions/0024-root-custody-and-the-signing-api/)).
  - **policy:** Cedar with a fixed schema ([0007](/decisions/0007-policy-and-sealed-grants/)).
  - **audit, with usage and limits:** the audit log, plus a usage class of records that is never dropped and the limit check on the request path ([0029](/decisions/0029-the-audit-log/), [0046](/decisions/0046-usage-records-are-never-dropped-and-balances-live-in-the-product/)). It serves the product as well as sluis.
- **The add-ons** are optional, each with a scope of its own, and the core does not depend on any of them:
  1. **PKI, SSH and database access,** the most important and the first add-on: leaf certificate profiles and revocation lists, short-lived SSH certificates from a sluis token under ritueel's SSH CA, and client certificates for PostgreSQL. With the KV add-on it completes the retirement of the v1 secrets store: until the cutover the key-value secrets go to a cloud parameter store, and PKI and SSH come here.
  2. **KV secrets:** versioned static secrets in stores that no tenant owns, with policy by path, a data key per store, a blocking audit fact for every successful access, and a Vault KV v2 subset that External Secrets reads ([0047](/decisions/0047-kv-is-an-add-on-of-stores-that-no-tenant-owns/)). It needs the slice of workload exchange for Kubernetes ServiceAccount tokens, pulled forward from parity.
  3. **Cloudflare:** the exporter's bucket driver, the edge purge and the R2 credentials.
  4. **GitHub:** GitHub Actions OpenID Connect as a workload proof in `exchange` and `policy`, and `adapter-github`.

An installation serves one boundary ([0008](/decisions/0008-boundaries-and-tenants/)). Its staff and operators sign in with sluis's own passkeys. Everyone else signs in through the upstream identity provider, and `exchange` turns the upstream token into a sluis token that carries the customer, the organisation and the product. Realms follow boundaries: a regulated boundary has a realm of its own, a product has a generic realm, and a central realm holds the end-user accounts, so the chain is end user, then the boundary's realm, then the central realm ([0045](/decisions/0045-customers-sign-in-upstream-and-the-sluis-token-carries-customer-org-and-product/)).

An installation may also run the foundation with the audit module only, to keep the audit trail of a product that does not use sluis for sign-in ([Audit](/concepts/audit/#audit-alone)). The foundation (store@, exporter@ and key@) and the modules are explained on [Families](/concepts/families/#the-foundation-and-the-modules).

## Phases

The phases are an order. Each opens when the one before it is done, except where it says otherwise. P2 comes before P3 ([0044](/decisions/0044-sluis-v2-is-a-core-building-blocks-and-add-ons/)).

0. **P0, records (now).** This page, the decision records and the requirement rows say the re-plan. The ritueel boundary is corrected in the pages that said ritueel publishes files for sluis. The board's `Product milestone` options and the issues change separately: as of 2026-11-12 the board still has the options First working version, v1 parity, CIAM upstream, Quota and Backlog.
1. **P1, the first working version: the core.** The local installation, plus the foundations every installation stands on. The local installation is Docker Compose on a workstation: one container per actor and per driver, built from the published images ([#1123](https://github.com/truvity/sluis/issues/1123)), with the minimal drivers (rqlite with one node as the store's engine, a SQLite audit index, a files blob, a spool or direct transport), software keys by default, sign-in through the generic OpenID Connect upstream tested against a real identity provider ([#1106](https://github.com/truvity/sluis/issues/1106)), and the audit log with Search ([#1120](https://github.com/truvity/sluis/issues/1120), [#1121](https://github.com/truvity/sluis/issues/1121), [#1122](https://github.com/truvity/sluis/issues/1122); [The local installation](/decisions/0011-runtimes-and-installations/#the-local-installation)).
   - **The core actors** are `entry`, `session`, `exchange`, `signer`, `policy` and `ca`, on the foundation of store@, exporter@ and key@. `ca` issues the token certificate under the node's intermediate; its other profiles are the PKI add-on. The `console` is not in this phase, so the first version has only the browser flows that sign-in and passkeys need. The actors serve the basic OpenID Connect flow (discovery and the key set, authorization with PKCE, tokens, refresh, UserInfo and revocation, form post), and passkeys and step-up ([#885](https://github.com/truvity/sluis/issues/885)).
   - **The three boards stay in this phase** (decision D2 A of 2026-11-12): the YubiKey PIV key driver on the cards, the PIN released from slot 87 to a locked `key@` (with the card driver checking the `KeyPlan`'s signature and the peer's slot 87 signature itself before it seals or opens), the mainline Ubuntu 26.04 and Rocky 10 images, and the three-node rqlite cluster ([Bare metal](/runtimes/bare-metal/)). The other board rows are Backlog. The boards keep the audit log on the local blob for now, because it is test data.
   - **Root custody** reaches the installation through the hand-off to ritueel ([#1066](https://github.com/truvity/sluis/issues/1066), [#1071](https://github.com/truvity/sluis/issues/1071)).
   - **exporter@ is in this phase with the directory driver,** the static key set and its publication report ([#1453](https://github.com/truvity/sluis/issues/1453)). The bucket driver, the edge purge and the R2 token ([#1454](https://github.com/truvity/sluis/issues/1454), [#817](https://github.com/truvity/sluis/issues/817)) are no longer part of the first version: they are the Cloudflare add-on, which P3 needs ([0009](/decisions/0009-export/#publishing-public-material)). Until then a revoked key leaves the key set that the directory driver publishes.
   - **GitHub is not in the core.** The `github-oidc` verifier in `exchange` and `policy` moves behind the GitHub add-on.
   - **The phase also holds** the published images with checksums and SBOMs, and no signature ([ADR 0013](/decisions/0013-release-train-packaging-and-distribution/#signing-and-checksums), [#1124](https://github.com/truvity/sluis/issues/1124)), and the integration tests of every command of the command table against the local installation in CI ([#1100](https://github.com/truvity/sluis/issues/1100)). The maintainer still signs each tag by hand.
   - **Moved out of the first version on 2026-11-07,** by the maintainer's scope decisions, and still out: workload identity ([#870](https://github.com/truvity/sluis/issues/870)), federation, the proof verifiers, the signing API ([#890](https://github.com/truvity/sluis/issues/890)), the console, and `ca` beyond the token certificate. The boards' rqlite has no TLS and listens on the board address behind a firewall, which is a known limit of the test installation; before any real PIN or real data goes on a board, the maintainer closes or accepts each known limit in writing ([REQ-DEPLOY-047](/requirements/deploy/#REQ-DEPLOY-047), [#1584](https://github.com/truvity/sluis/issues/1584)).
   - **Done when** the example bootstrap file for local starts under Docker Compose from the published images, the integration tests run against it in CI, and the three boards run the same spine with a YubiKey as the key driver. Every command in the [first-version command table](/reference/cli/#the-first-working-versions-commands) exists, and each has a test in CI against the local installation; card commands are attested from a board run. The core starts and passes these without any add-on.
2. **P2, the identity and audit blocks.**
   - **Person exchange from the upstream token.** `exchange` accepts an upstream token (RFC 8693) from the trusted issuer of its boundary's realm, and issues a sluis token with the customer, the organisation and the product ([#782](https://github.com/truvity/sluis/issues/782), [#785](https://github.com/truvity/sluis/issues/785), [#961](https://github.com/truvity/sluis/issues/961), [0045](/decisions/0045-customers-sign-in-upstream-and-the-sluis-token-carries-customer-org-and-product/)). Services call each other with the sluis token.
   - **Usage and limits.** A usage stream that is never dropped, with an idempotency key on every record, and the limit check on the request path ([0046](/decisions/0046-usage-records-are-never-dropped-and-balances-live-in-the-product/), [#841](https://github.com/truvity/sluis/issues/841)).
   - **Done when** a token from the upstream test realm is exchanged for a sluis token with the three claims, a usage record whose store fails fails its operation, and a repeated record is stored once.
3. **P3, the PKI, SSH and database add-on, and the cutover of the v1 platform.**
   - **The add-on.** Leaf profiles and the revocation list ([#913](https://github.com/truvity/sluis/issues/913)); `ssh-ca`, which turns a sluis token into a short-lived SSH user certificate and issues host certificates, under the SSH CA that ritueel lists ([#925](https://github.com/truvity/sluis/issues/925), [0023](/decisions/0023-certificate-authorities/#ssh)); and PostgreSQL client certificates for CloudNativePG ([#926](https://github.com/truvity/sluis/issues/926)); and the KV add-on, with its slice of workload exchange ([0047](/decisions/0047-kv-is-an-add-on-of-stores-that-no-tenant-owns/), [#798](https://github.com/truvity/sluis/issues/798)). Real roots come from ritueel; until ritueel has the SSH CA key list, the add-on runs on the harness's test root.
   - **The cutover of the maintainer's v1 platform** (decision D5 A): once sluis is at v1 parity for what that platform uses, the whole platform switches to the three-board install. The audit log moves from the local spool to buckets on R2, so the Cloudflare add-on is built in this phase because the cutover needs it. Which parity rows that platform uses is mapped separately; the rest of the parity group is Backlog. The v1 secrets store is then retired in waves: PKI and SSH go to the PKI add-on, and the platform's External Secrets switches from the parameter store to sluis KV app by app, with a rollback ([0047](/decisions/0047-kv-is-an-add-on-of-stores-that-no-tenant-owns/)).
   - **Done when** an operator gets an SSH certificate and a PostgreSQL client certificate from a sluis token, and the platform runs on the boards install with its audit on R2.
4. **P4, block extraction.** A runtime registry for store, a schema extension for policy and a key library, so that a product can reuse a block. Until then no new coupling of domain types into a block.

:::note[Proposed]
Both the Kubernetes and the Lambda installations stay as v2 targets (maintainer decision D9, 2026-11-12). A mixed shape is allowed, where some sluis parts run on Kubernetes beside another installation, for example for the CloudNativePG part of the add-on. Its design is open ([#926](https://github.com/truvity/sluis/issues/926)).
:::

## Cancelled

By the maintainer's decisions of 2026-11-12 (D1 B, D4 A, D7 A) the following are no longer planned. Their records are superseded, and their requirement rows are withdrawn.

- **The CIAM upstream milestone:** the customer-facing sign-in profile (FAPI 2.0, PAR, DPoP and private-key client authentication), customer pages, customer connections, the end-user lifecycle, pairwise subjects per sector and the login abuse limits ([0031](/decisions/0031-ciam-is-a-broker/), [0033](/decisions/0033-customer-connections/), [0034](/decisions/0034-end-users-and-upstream-signals/), [0035](/decisions/0035-customer-pages/), [0038](/decisions/0038-fapi-2-profile/)). Customers sign in through the upstream identity provider ([0045](/decisions/0045-customers-sign-in-upstream-and-the-sluis-token-carries-customer-org-and-product/)).
- **The Quota milestone:** the allowance and its balance inside sluis ([0039](/decisions/0039-quota-allowance/)). Plans and balances live on the product side; sluis keeps usage and a limit check ([0046](/decisions/0046-usage-records-are-never-dropped-and-balances-live-in-the-product/)).
- **OpenBao as a driver.**

## Delivery order

The tested [installations](/runtimes/) are built in this order:

1. **local first,** with the core (P1). The three boards are part of P1 too, and so is the hardware base they need.
2. **The boards are the home of the v1 platform's cutover** in P3: three single-board computers, a YubiKey in each node, the store and the audit index on rqlite, and audit logs on R2 with the Cloudflare add-on ([Bare metal](/runtimes/bare-metal/)).
3. **Lambda and Kubernetes** stay as v2 targets, needed for v1 parity (maintainer decision D9, 2026-11-12). They come after the cutover of the v1 platform to the three boards (P3), on the way to the remaining v1 installations ([ADR 0011](/decisions/0011-runtimes-and-installations/#delivery-order)). A mixed shape, where some sluis parts run on Kubernetes beside another installation, is allowed; its design is open ([#926](https://github.com/truvity/sluis/issues/926)).

EC2 is a possible bare-metal installation, not a delivery target, and not tested. Other installations are possible and untested. The order is reviewed when each installation ships, and ADR 0011 records any change.

## Later

**The backlog** holds the plans that the re-plan of 2026-11-12 does not serve: the v1 parity group except the rows the cutover and the PKI add-on need, the isolation harness and generators, the extra board rows, the extras of the Cloudflare and GitHub add-ons, the audit read API and front, the console, the reconcilers, and libraries in languages other than Go and Rust. The board and the requirement rows follow this page when the maintainer's script has moved the issues.

Work planned after that is marked Later on the board. It includes CIBA, in poll mode with a passkey on the approving device, once a real consumer exists ([#980](https://github.com/truvity/sluis/issues/980)); ACME for host certificates ([#978](https://github.com/truvity/sluis/issues/978)); device login ([#855](https://github.com/truvity/sluis/issues/855)); a FIPS build variant when a customer needs one ([#868](https://github.com/truvity/sluis/issues/868)); and other clouds and stores. Garage as the boards' blob store is backlog, because it ignores conditional writes ([#982](https://github.com/truvity/sluis/issues/982)).

**Staff keys** are in Backlog too: card binding per employee, the company's own OpenPGP keys for its staff (certified by sluis, listed in a staff keyring, and synced to staff GitHub accounts), and the same binding for a customer's JWK ([ADR 0043](/decisions/0043-a-person-binds-their-own-keys-to-their-identity-in-sluis/), [ADR 0042](/decisions/0042-sluis-syncs-company-issued-openpgp-keys-to-staff-github-accounts/), [#1719](https://github.com/truvity/sluis/issues/1719), [#1718](https://github.com/truvity/sluis/issues/1718), [#1076](https://github.com/truvity/sluis/issues/1076)). The maintainer decided on 2026-11-07 to move "card binding per employee and GPG key management" out of the first working version, and to keep it in Backlog. It is not scheduled and no phase waits for it. The ritueel half of ADR 0043 is superseded ([ADR 0044](/decisions/0044-sluis-v2-is-a-core-building-blocks-and-add-ons/#staff-keys-and-ritueel)): ritueel dropped staff keys, so there is no ritueel card helper, no shared staff bundle and no trust-signature ceremony. What it needs first: the hardware-attested sign-in, the directory and `adapter-github` (the GitHub add-on), and, before the build, the measurements against GitHub and the conformance test on a real card that the two records list under Follow-ups. The OpenPGP subkeys of the boards' nodes and the passkey sign-in tiers are not part of it and stay where they are.

**Signing of release artifacts** is in Backlog as well. The maintainer decided on 2026-11-07 that neither the keyless signing (cosign signatures, build-provenance and SBOM attestations) nor the OpenPGP signing of releases belongs to the first working version or to v1 parity. A release carries checksums and SBOMs, and the maintainer signs each tag by hand. The requirements REQ-SUPPLY-001, 002, 007, 008, 017, 018 and 043 are in Backlog, and the work waits with the staff key and GPG work ([ADR 0013](/decisions/0013-release-train-packaging-and-distribution/#signing-and-checksums), [#874](https://github.com/truvity/sluis/issues/874), [#1013](https://github.com/truvity/sluis/issues/1013), [#1074](https://github.com/truvity/sluis/issues/1074)). The signing API ([#890](https://github.com/truvity/sluis/issues/890)) is a separate thing and is in v1 parity.

## Where the work is tracked

The v1 features that v2 must match are issues labelled [`parity`](https://github.com/truvity/sluis/issues?q=is%3Aissue+label%3Aparity), listed on the [v1 parity checklist](/features/). Spike results are in the decision records they settled, such as [ADR 0012](/decisions/0012-the-language-follows-the-executable/#the-spikes-are-gates), and on the issue of each spike.
