# 0013 — One repository, one version, one release train, and packaging follows the runtime

**Status:** Accepted
**Date:** 2026-11-03
**Amended:** 2026-11-04, `sluis config check` runs the store executable as a helper ([One version](/decisions/0013-release-train-packaging-and-distribution/#one-version)); 2026-11-06, the boards run Ubuntu 26.04 and Rocky Linux 10, so the board exception is no longer used ([Supported platforms](/decisions/0013-release-train-packaging-and-distribution/#supported-platforms)), and every distribution form declares its runtime dependencies in one matrix ([Packaging per runtime](/decisions/0013-release-train-packaging-and-distribution/#packaging-per-runtime)); 2026-11-07, no release artifact is signed in the first working version or in v1 parity ([Signing and checksums](/decisions/0013-release-train-packaging-and-distribution/#signing-and-checksums)); 2026-11-08, `policy` and `entry`, the audit front included, are in the foundation package `sluis`, the command-line tool is the package `sluis-cli` and has no dependency on systemd, `sluis` depends on `sluis-cli`, a driver package is named for the driver's registry name, `sluis-driver-<owner>-<name>`, and may recommend the driver of another owner that its unit requires ([Packaging per runtime](/decisions/0013-release-train-packaging-and-distribution/#packaging-per-runtime))

Proposal: [issue #909](https://github.com/truvity/sluis/issues/909).

## Context

v1 ships from one repository on one version line, 1.x, with no major-version suffix on its Go module path. v1 ADR 0042 put every v1 product on one train, so that a change touching two of them is one pull request and one release. The early v2 design added build profiles (`aws`, `selfhosted`, `kubernetes`, `dev`) that chose which parts went into a build.

v2 is a clean start on `main` ([0001](/decisions/0001-v1-and-v2-lines/)) and a different set of processes: actors, drivers, a node agent, a host service and one command-line tool ([0002](/decisions/0002-families-of-actors/)), some in Go and some in Rust ([0012](/decisions/0012-the-language-follows-the-executable/)). It runs in three runtimes ([0011](/decisions/0011-runtimes-and-installations/#runtime-kinds)), and each installs software differently: a package manager on a host, a function archive on serverless, an image on a cluster. The executable is what carries over between runtimes, not the package.

Every installation runs the foundation, store@, key@ and exporter@, and the modules it needs ([0002](/decisions/0002-families-of-actors/#the-foundation-and-the-modules)). A driver belongs to one holder and is private to it ([0005](/decisions/0005-the-store/#drivers)), so what a host installs follows the holders and modules it runs.

Two platform facts are hard constraints. The YubiKey driver talks to the smart-card service through cgo against pcsc-lite, so it cannot be cross-compiled on a plain build host. Lambda allows five layers and 250 MB unzipped per function, and every process in a function shares its role, so the function is the credential scope; for sluis the layer count is the binding limit.

## Decision

### One version

- **Every artifact of a release carries the same version** and ships together: packages, tarballs, Lambda zips, images, charts and the console bundle. A component with no change still ships. This continues v1 ADR 0042 for v2.
- **v2 versions are v2.x.y,** and the main Go module path ends in `/v2` (`github.com/truvity/sluis/v2`). Any further Go module takes the same suffix, and all modules are tagged at one commit.
- **Before v2.0.0 every release is a pre-release, `v2.0.0-alpha.N`,** tagged on `main`, each a full release of every artifact. Nothing is stable before v2.0.0: no compatibility promise holds between two alphas, images and charts carry no `latest` or other floating tag, and the GitHub release is marked as a pre-release.
- **One build tool: GoReleaser v2, open-source edition,** for Go and Rust executables alike, with one SBOM generator and one build definition. The Rust executables are built with cargo-zigbuild, current crates and rustls, as static musl binaries, except the binaries that link `libpcsclite`. GoReleaser builds the images from the binaries of the same run with `dockers_v2`, and truvity/ocictl packages and pushes the Helm chart from the same output, with every image pinned by digest. There is no FIPS build in 2.0 ([0006](/decisions/0006-keys-and-sealing/#algorithms)).
- **The YubiKey driver, and the build of key@ that links `piv-go`, are built in a native job per architecture,** inside a pinned build userland (Ubuntu 22.04, glibc 2.35, which is a build image and not a supported platform), and a test fails the job when an executable asks for a glibc symbol newer than 2.34, the glibc of the oldest supported system, so they run on every supported glibc (`REQ-DEPLOY-032`). The jobs' outputs join the rest of the release.
- **One command-line tool, `sluis`, with subcommands** for operators and users, such as `sluis config check`, `sluis doctor`, `sluis trust sync` and `sluis key request|install|status`. Root ceremonies belong to [ritueel](https://ritueel.id). Actors, drivers, the node agent and the host service are separate executables, one per process, because each runs as its own user, unit, function or container.
- **`sluis config check` runs the store executable of the same release as a helper** ([0012](/decisions/0012-the-language-follows-the-executable/#per-actor-table)). The CLI looks for it in this order: its `--helper` flag, the `SLUIS_STORE_HELPER` variable, the install path `../libexec/sluis/actors/store` beside the CLI's own directory, and `store` in that directory. So a host with the `sluis-cli` and `sluis-store` packages uses the package's store, and a tarball that holds both executables in one directory works as it is unpacked. The CLI refuses a helper whose version is not its own. The helper is a Linux executable, so `config check` runs on Linux only.

### Packaging per runtime

There are no build profiles: the runtime decides the packaging, and every artifact is built for amd64 and arm64. `dev` is not a build; it is the local installation, which runs the published images ([0011](/decisions/0011-runtimes-and-installations/#the-local-installation)).

| Runtime | Packaging |
|---|---|
| bare-metal | `.deb` and `.rpm` packages split by holder, module and driver, in apt and dnf repositories, and a tarball |
| serverless | A zip per executable, a function per actor instance, at most three sluis layers per function |
| kubernetes | One multi-arch OCI image per process, and one Helm chart with the images pinned by digest |

- **The install directory is `/usr/libexec/sluis/{actors,drivers,node,vendor}/<short-name>`,** the same in a package, a tarball and an image. The adapters are actors. A driver sits in the private directory of its owner, `drivers/<owner>/<name>`, where the owner is the actor whose port it serves.
- **Host packages follow the foundation and the modules:**
  - **`sluis-cli`** (the command-line tool at `/usr/bin/sluis`, with `sluis agent`, and no dependency on systemd, so that a workstation without it installs the CLI alone), **`sluis`** (the foundation's `policy` and `entry`, with both units of `entry`, the identity front and the audit front, so a host that runs the audit module reaches `entry` without a work actor, the `sluis trust sync` timer and their units; it depends on `sluis-cli` and on systemd) and **`sluis-node`**;
  - **the foundation:** `sluis-store`, `sluis-key` and `sluis-exporter`, each with its actor and its units;
  - **`sluis-driver-<name>`,** one per driver executable, named for its registry name (`sluis-driver-<owner>-<name>`), with its system dependencies, for example `sluis-driver-key-yubikey-piv` on pcscd, a CCID driver, libpcsclite and polkit, and `sluis-driver-store-rqlite` shipping `rqlited` under `vendor/`. A driver package depends on the package of its owner (and may recommend the driver package of another owner that its unit requires, which is the one weak edge: the indexer's file driver recommends the writer's). It installs no service for an operator to start: the owner's unit starts the driver and only the owner can open its socket ([0003](/decisions/0003-units-transports-and-fusion/#units));
  - **the identity module:** `sluis-identity` (the work actors other than `quota`, `policy` and `entry`, the first-party adapters included) and `sluis-console`;
  - **the audit module:** `sluis-audit-writer`, which ships the writer and the witness, and `sluis-audit-search`;
  - **the quota module:** `sluis-quota`;
  - **`sluis-host`.**
- **Every distribution form declares its runtime dependencies,** and the [runtime dependency matrix](/distribution/dependencies/) is the one list of them: a package's `Depends`, `Recommends` and `Suggests`, what a container image installs, what a Lambda layer or extension bundles, and what the boards deploy requires of the board image. A dependency sits on the narrowest package that needs it, so a host that does not run the card driver installs no pcscd. A form that is not built yet is marked so in the matrix (`REQ-DEPLOY-038`).
- **A module package depends on the foundation packages and on no other module,** and no package depends on a driver package it does not use. A host that runs the foundation with the audit module only installs no work actor of the identity module and no driver it does not run.
- **Meta-packages exist only for the bare-metal installations that install from packages:** `sluis-install-boards`. Local runs images, so there is no `sluis-install-local`.
- **`sluis-host` is a separate root host service, mainly for SSH.** It never listens on the network; it fetches the signed SSH principals bundle ([0023](/decisions/0023-certificate-authorities/#ssh)), verifies it, writes it atomically and keeps the last good one.
- **The trust bundle reaches hosts through the `sluis` package.** `sluis trust enroll --url … --root-pin <spki-hash>` turns on `sluis-trust-sync.timer`; the sync checks the bundle ([0022](/decisions/0022-workload-identity-and-host-enrolment/#the-trust-bundle)) and the root list ([0024](/decisions/0024-root-custody-and-the-signing-api/#root-pins-and-the-root-list)), writes the anchors and runs the distribution's trust update; its unit may write nothing else. sluis generates no per-installation packages. On Kubernetes the bundle reaches pods through a trust-manager source or a ClusterTrustBundle.
- **Lambda:** one function per actor instance and one zip per executable, named `sluis-<kind>-<name>_<version>_<arch>.zip`. Functions, schedules, roles and invoke grants are derived from the actor registry ([0002](/decisions/0002-families-of-actors/#registries-generate-the-enforcement)). A work function carries no driver. A holder's function carries its drivers as extensions: one Rust extension that implements the AWS ports the holder needs (for store@ the AppConfig, SSM and DynamoDB ports; for key@ the KMS port). The three sluis layers are the edge layer (`entry` only), the drivers layer and the configuration layer, so at least two stay free for the operator. The executable is the package's binary renamed `bootstrap`, behind the kit's invoke adapter; only `entry` has a listener and uses the Lambda Web Adapter, pinned and vendored ([0003](/decisions/0003-units-transports-and-fusion/#listeners)). arm64 is the default. sluis publishes no public layer ARNs: an installation verifies the zips and publishes the layers into its own account. Not published for Lambda: the YubiKey driver, `sluis-node`, rqlite, and every driver that needs a disk or a long-running process.
- **Images:** one image per process, holding one executable at the package's path, byte for byte, with the source package in a label. Bases are distroless static, and distroless with glibc and a pinned pcsc-lite for cgo binaries, each pinned by digest. Names are flat, `ghcr.io/truvity/sluis/<kind>-<name>` (for example `ghcr.io/truvity/sluis/actor-entry`), and no image is named `sluis`, because that name belongs to v1's images. Tags are the release version, and the digest is the reference; each release lists every image digest in a `release-images.txt` file. **One image set serves the local installation and Kubernetes**, and a release test compares the images' binaries with the packages' files by hash.
- **Helm, from the parity milestone:** one `sluis` chart with a piece selector and the presets `install`, `audit-install`, `quota-install` and `kubernetes-dev`, and no subcharts, so a writer and a reader always come from one release. A holder's pod runs the holder's image with its drivers as native sidecar containers. Operators such as cert-manager are prerequisites the chart checks for. The cert-manager issuer has a chart of its own, with its CRDs and RBAC; the certificate sidecar is an image plus a documented container snippet. The chart version is the release version, at `ghcr.io/truvity/sluis/charts/sluis`. The console runs as its own Deployment behind the same route as `entry`.
- **One S3-compatible blob driver** for S3 and R2, owned by the audit piece that writes the blob. It takes its credentials from the platform: STS through web identity on AWS, and on Cloudflare the `cloud-cloudflare` driver, which mints R2 temporary credentials scoped to one bucket and prefix, signed locally with a per-boundary parent token. The parent token is a platform-provided credential of that audit piece, written by IaC (a systemd credential on a board). The driver is separate from the Cloudflare minter of tenant credentials ([0025](/decisions/0025-integrations/#credential-minters)), though they share a library.
- **The console is a separate artifact,** a bundle of static files built once per release and served same-origin with the API: a directory from `sluis-console` on bare-metal, the bucket behind the API gateway on serverless, its own Deployment on Kubernetes.

### Supported platforms

- **Operating systems:** Ubuntu 26.04 LTS, Rocky Linux (the latest stable, 10.x) and Amazon Linux 2023, on amd64 and arm64. The boards are all aarch64: since 2026-11-06 two run Ubuntu 26.04 and one runs Rocky Linux 10 with SELinux enforcing, on current mainline-based kernels (the distribution's own on Ubuntu, the Kmods SIG kernel on Rocky). The facts per distribution are on [Bare-metal](/runtimes/bare-metal/#supported-operating-systems).
- **The systemd floor is 252,** the version in Amazon Linux 2023. Generated units may rely on what 252 provides, such as `LoadCredentialEncrypted=` and `ExecPaths=`.
- **Serverless and Kubernetes have no host distribution.**
- **A board image older than the floor is a declared exception,** not a supported platform: the units read `LoadCredentialEncrypted=` (systemd 250 and later; the floor is 252), so the boards deploy refuses to write a credential there, and `sluis doctor` warns where its kernel fails the randomness checklist. Until 2026-11-06 the boards ran a vendor image of Ubuntu 22.04 (systemd 249) under this exception; they were reinstalled that day on the supported systems above, so no board uses it now. Key material is never affected: it stays in the card.

### Distribution

- **Everything is served from an R2 bucket, without redirects:** `apt/` and `dnf/` repositories, `bin/<version>/` tarballs, `lambda/<version>/` functions, layers and extensions, `checksums/<version>/` and `keys/`, and a `latest` pointer. apt and dnf handle redirects unreliably, and a redirect is one more place to point a repository elsewhere.
- **GitHub Releases is the immutable record.** Each release holds the same files; when a file on R2 and on the release differ, the release is right.
- **OCI images and charts are on the GitHub container registry.** The website is a separate thing ([0014](/decisions/0014-the-site-is-static-on-cloudflare-workers/)).

### Compatibility between releases

- **The rules of this section hold from v2.0.0.** Between two alphas anything may change, and the CHANGELOG says what did.
- **Compatibility follows semantic versioning.** A breaking change ships in a major release, or in a minor release that says so in the CHANGELOG, announces it and carries an upgrade note; stored data stays readable by the next release; protocol contracts are checked for breaking changes ([GOVERNANCE.md](https://github.com/truvity/sluis/blob/main/GOVERNANCE.md)).
- **The configuration schema and its identifiers are public contract.** A published `$id` never changes; an incompatible schema is a new version under a new path, beside the old one ([0004](/decisions/0004-the-data-model/#schemas-are-protobuf)).
- **Removed configuration is refused, never silently ignored.** A key that no longer means anything fails validation with a message naming its replacement, as in v1 ADR 0007.
- **Artifacts of one release are built, tested and shipped together, and each also works with those of the previous release of the same major.** A writer and a reader, a chart and its images, a package and its drivers come from one release, and a rolling deployment runs two neighbouring releases at once ([0015](/decisions/0015-evolution-and-compatibility/#n-and-n-1-inside-a-major-version)).

### Signing and checksums

- **From the first alpha, every release carries checksums, SBOMs and keyless Sigstore attestations** (decided by the maintainer on 2026-11-01): a `SHA256SUMS` list and a `.sha256` per file; an SPDX JSON SBOM per archive and per image, made by syft, with the Rust crates recorded by `cargo auditable`; GitHub build-provenance attestations on the archives, packages, Lambda zips and image digests, and SBOM attestations bound to them; and a keyless `cosign sign` of each image digest, beside its attestation. All are made by the CI build with its GitHub OIDC token and no stored secret.
- **Sigstore says how a file was built, not who vouches for it.** Its trust rests on GitHub's OIDC identity and the public Sigstore instance, so it does not replace the OpenPGP release key, and `sluis-node` does not trust it alone ([0012](/decisions/0012-the-language-follows-the-executable/#per-actor-table)).
- **Nothing is signed with OpenPGP before the roots exist.** The OpenPGP signatures wait until the root ceremony and its drill have run in ritueel.
- **From then on, releases are also signed through sluis's own signing API** with a release subkey held in a cloud key service ([0024](/decisions/0024-root-custody-and-the-signing-api/#signed-releases)): detached signatures first, then signed apt and dnf repository metadata.

Amendment of 2026-11-07. The maintainer decided that no release artifact is signed in the first working version, and not in v1 parity either: no keyless cosign signature, no build-provenance or SBOM attestation, and no OpenPGP signature. A release carries `SHA256SUMS`, the per-file checksums and the SBOMs, and the maintainer still signs each tag by hand. Signing release artifacts, keyless or OpenPGP, is in Backlog with the staff key and GPG work ([Roadmap](/roadmap/#later)). The bullets above, and the two lines of Consequences that name attestations, describe that work for when it returns and do not apply until then. This takes the road "Checksums only until the first OpenPGP-signed release" of Roads not taken, and accepts its cost: nothing ties a release to the build that made it except the checksums and the signed tag. The signing API of [0024](/decisions/0024-root-custody-and-the-signing-api/#the-signing-api) is a separate thing and moves to v1 parity.

## Consequences

- `sluis config check` needs two executables of one release, the CLI and store. A pipeline that checks config before it publishes installs both, on Linux.
- One tag produces everything, so no one needs a compatibility table between components. A small fix releases every artifact, including unchanged ones.
- Every consumer of a v1 Go module changes its import path once, when it moves to v2; both lines can sit in one build graph during the migration.
- Two toolchains build one train. If the Cargo workspace does not build under GoReleaser, the train needs a special-case job.
- Two native jobs per release build the YubiKey driver and the card build of key@, and a failure in either blocks the release.
- A few dozen images per architecture are built and published; each digest names one thing, and a scanner reports on the binary a container actually runs.
- The Lambda limits are a build-time budget: the build fails when a function's drivers need more than three sluis layers. Per-actor functions chain cold starts on a first request, and every data access of a work function is an invoke of store@'s function ([0003](/decisions/0003-units-transports-and-fusion/#transports)); provisioned concurrency on `entry`, `signer` and the holders is the lever if that is too slow.
- A package per driver means more packages to build and test; the meta-package is the short list an operator installs. A KMS-only host installs no card driver and no pcscd.
- Prefix scoping on R2 depends on temporary credentials, so the parent token is a per-boundary credential that has to be rotated by the operator.
- **R2 temporary credentials minted through the API showed no acceptance delay** (MEASURED 2026-11-06, [spike #1479](https://github.com/truvity/sluis/pull/1479), README with the method: 30 credentials, one every 10 seconds, each probed every 500 ms and then for 40 seconds after its first accept). Time to the first accept was 0 s at p50, p95 and maximum, every credential was accepted at its first attempt, and none was refused with 401 or 403 after an accept. The run excludes an effect of the size v1 saw (about 14 % of rotations) from one place and one moment, not a rarer one. What it covers and what it does not, by consumer:
  - **The audit blob driver on R2** takes its credentials from the `cloud-cloudflare` driver. The spike measured the form that the API mints. This record says the driver signs them locally with the parent token, and that form was **not measured** (UNVERIFIED). One retry on 401 or 403 is the rule for the driver ([REQ-AUDIT-174](/requirements/audit/#REQ-AUDIT-174)); whether it needs a hold-back too depends on the locally signed form.
  - **The exporter's destination credential** is platform-provided, a systemd credential, a role or a service account, and for R2 it may be a static API token. That is the mechanism v1 measured refused for up to about 34 seconds, so the spike says nothing about it (UNVERIFIED), and the 60 seconds of [REQ-EXPORT-028](/requirements/export/#REQ-EXPORT-028) depend on it ([REQ-EXPORT-029](/requirements/export/#REQ-EXPORT-029)).
  - **A newly created parent token** is the same case as a static token, so the result does not cover a rotation of the parent token.
- On every supported platform, the boards included, unit credentials are encrypted at rest under the host key. The board exception, which no board uses since 2026-11-06, was the only place where they were protected by file mode and a private state directory instead. Key material is never affected: it stays in the card.
- The dependencies of every form are in one matrix that package metadata, images and layers are checked against; until the packages, release images, chart and Lambda artifacts are built, their columns are a specification, and the matrix lists the gaps.
- R2 is a single provider for downloads; GitHub Releases is the second copy and wins a disagreement.
- Until the first OpenPGP-signed release, a user checks downloads against checksums and Sigstore attestations (`gh attestation verify`, `cosign verify`), and an apt or dnf repository cannot be verified by its signature. The attestations prove which workflow built a file from which commit, nothing more.
- GHCR has no OCI referrers API (measured 2026-11-01), so attestations and signatures are found through the fallback tag `sha256-<digest>`; a registry mirror must copy those tags too.
- The first working version ships images and no chart; a chart that installs them follows at parity.
- The pages [Packages](/distribution/packages/) and [Platforms](/distribution/packages/#supported-platforms) describe this record; when they disagree, the page is fixed.

## Roads not taken

- **Keep the build profiles.** A profile mixed the runtime with the provider and the use, and a build that is not the one tested is the one that runs.
- **Independent versions per component or module.** A user would need a compatibility table between components released from one commit; v1 ADR 0042 rejected it for the same reason.
- **store@'s validation linked into the `sluis` binary.** The CLI is Go and store@ is Rust; linking Rust into the Go binary through cgo would give up its static cross-compiled build for one command.
- **One binary for everything, selected by subcommand.** An actor's unit could then execute every other actor's code; only the CLI is one binary.
- **ko for the images.** It builds Go only and puts the binary under its own path, so the Rust executables and the rule that an image holds the package's file byte for byte would not hold.
- **The four-segment image names `ghcr.io/truvity/sluis/<kind>/<name>`.** Not shown to work on GHCR, where the flat three-segment form is.
- **Checksums only until the first OpenPGP-signed release.** Nobody could tie the first images to the build that made them, although keyless provenance needs no root.
- **A separate Cargo release tool for the Rust executables.** It would be a second train with its own SBOM and signing to keep in step.
- **Drivers inside the holders' packages, or one `sluis-drivers` package.** A KMS-only host would install pcscd and the card driver, or every host every driver and its system dependencies.
- **A driver package an operator starts as a service.** Only the owner may open a driver's socket, so a service of its own would be a second way to start the driver.
- **A container image for Lambda.** Layers do not apply to images, so the adapter and extensions would be baked into every image.
- **An image per package, or a distribution base image with the packages installed.** Containers would carry other actors' binaries, a shell and a package manager.
- **A chart per piece, or an umbrella chart with subcharts.** A writer and a reader could come from different releases, and subcharts cannot see the parent's generated schema.
- **Downloads through redirects, or from GitHub Releases alone.** apt and dnf handle redirects unreliably, and GitHub Releases is not an apt or dnf repository.
- **Lower the systemd floor to the boards' image.** Every platform would give up encrypted credentials for one vendor image.
- **Keep the vendor board image as a standing exception.** It cost the boards encrypted credentials and a deploy path for a pcscd without polkit; the boards were reinstalled on the supported systems instead (2026-11-06).
- **Dependencies written separately in each form's metadata.** The package, the image and the layer would drift apart, as the card path's packages already differ by family; one matrix is the list they are checked against.
