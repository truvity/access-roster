# 0003 — Deprecate and remove the access-proxy chart

**Status:** Accepted
**Date:** 2026-09-25

## Context

`access-proxy` wraps upstream `oauth2-proxy` as Envoy Gateway's external
authorization backend, giving a console five things from a hostname and a
backend name: login, a session that outlives a token, a forwarded bearer,
global sign-out, and a posture
([design/access-proxy.md#purpose](../design/access-proxy.md#purpose)). It
was chosen over the gateway's native OIDC filter for four properties a
bare token in a cookie cannot give: real session management, room for a
large token, global logout, and background refresh
([design/access-proxy.md](../design/access-proxy.md)).

Of those four, three are matched by a console that signs in as a client
of the issuer directly, on class A behaviour as defined in
[0001](0001-sessions-and-an-absolute-limit.md): it refreshes against the
issuer, so revocation reaches it at the next refresh, and `ttl_cap`
bounds that window from the issuer's side exactly as `session.refresh`
does today from the proxy's. The fourth — a **server-side session
store** — is real, but it buys less than it appears to: `oauth2-proxy`
encrypts each session with a key that lives only in the user's cookie,
so nothing server-side, including a Back-Channel Logout receiver, can
ever open a session it holds
([design/access-roster.md#telling-the-relying-party-back-channel-logout](../design/access-roster.md#telling-the-relying-party-back-channel-logout)).
The one advantage a server-side store would normally give — a sign-out
that closes every window at once, server to server — is exactly the one
this store cannot provide.

What the proxy costs to keep, per console: a Deployment, a share of a
Valkey, a confidential client and its secret, and a cookie secret that
must never be generated by a chart render an operator does not control
([design/access-proxy.md](../design/access-proxy.md), *Decided
2026-09-08*). For a console that can run its own OpenID flow, that is
infrastructure bought for a session-store property the proxy cannot
actually make good on.

## Decision

**Gateway-native OIDC is the default for a new console going forward,
using [0001](0001-sessions-and-an-absolute-limit.md)'s class-A shape.** A
console that can run an authorization-code flow signs in as a declared
client of the issuer, the way the directory console already does since
0.12
([design/access-roster.md#the-console](../design/access-roster.md#the-console)).

`access-proxy` is not deleted today. One page stays, narrowed to its
remaining honest use: a gateway that is **not** Envoy Gateway, fronting a
console with no OpenID flow of its own, using `oauth2-proxy` with a
declared confidential client the way the chart already wires it. Every
other case migrates to native OIDC.

**Removal is scheduled inside the 1.x line** (per
[0007](0007-breaking-changes-inside-1x.md)), once no known consumer of
the chart remains. The chart is not held past that point for
compatibility's sake — a component with zero consumers documented as a
design decision is the appendix entry
[design/access-roster.md#appendix-what-was-removed-and-why](../design/access-roster.md#appendix-what-was-removed-and-why)
is for.

## Consequences

A console migrating off `access-proxy` moves from `posture: groups` or
`authenticated` at the gateway to `requires` on its own declared client —
the same gate, checked at the same three points
([design/access-roster.md#who-may-open-which-console](../design/access-roster.md#who-may-open-which-console))
instead of at the proxy's route. It gains Back-Channel Logout as an
option it did not have behind the proxy, and loses nothing the proxy
was actually delivering, per the analysis above.

A console that genuinely cannot run an OpenID flow — because it is not
served behind Envoy Gateway, or because its framework has no OIDC client
of its own — keeps `access-proxy` for as long as that is true, on the
page that survives this decision.

## Alternatives considered

**Keep `access-proxy` as the default and build Back-Channel Logout
support into it anyway.** Rejected: the constraint is upstream, in how
`oauth2-proxy` encrypts a session, not in this chart's wiring around it;
nothing this repository could add reaches inside a browser-held key.

**Replace `oauth2-proxy` with a proxy of our own that keeps sessions
server-side and can be told to end one.** Rejected for the same reason
[design/access-proxy.md#why-not-something-else](../design/access-proxy.md#why-not-something-else)
gives for not writing the current proxy: identity-critical code on every
console's request path, to recover a property that native OIDC already
gives any console able to run it — which describes most of the consoles
this repository knows of.
