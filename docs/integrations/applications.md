These are **client profiles**: things that sign in to sluis or ask it for a token, and that sluis never calls. They have no adapter, no connection, no process and no credential of their own. Each is a client entry (and sometimes a resource entry): an `InstallationClient` in config for the installation's own clients, or a `TenantClient` that a tenant admin or a product registers for a tenant, inside the bounds of a client template ([0021](/decisions/0021-clients/#the-client-declaration)). `sluis config check` checks the configuration like the rest.

## What it's for

- **A deployment console signs people in** (a GitOps UI, a promotion tool). It is configured with sluis's issuer URL and a client; the `groups` claim decides who administers and who only views.
- **An application has its own sign-in.** It speaks OpenID Connect to sluis directly and reads the `groups` claim from the token.
- **A console with no sign-in of its own** sits behind a gateway with OIDC support, or a reverse proxy that runs the flow and forwards a bearer token.
- **An MCP server asks who is calling it.** An AI agent discovers sluis as the authorization server for a resource, signs in on a person's behalf through a consent page that is never silent, and presents a token for that resource. A stock server sits behind a sidecar that verifies tokens and serves the protected-resource metadata ([0021](/decisions/0021-clients/#mcp-authorization)).
- **cert-manager obtains certificates** for workloads from the `ca` actor through an external issuer, so the cluster needs no CA key of its own ([0023](/decisions/0023-certificate-authorities/#x509)).
- **An infrastructure-as-code program gets provider tokens** (a GitHub token, a Cloudflare token) by token exchange with the identity of its CI job, instead of a stored credential. The tokens come from the minters of the [GitHub](/integrations/github/) and [Cloudflare](/integrations/cloud/#cloudflare) connections.

## Integration kinds

None. What these clients use is core's: the OIDC endpoints, token exchange, resources, and the [`ca`](/concepts/families/) actor.

## What sluis asks the vendor for

Nothing. The vendor, if there is one, is the client, and it is configured to trust sluis:

| Client | What the operator configures on its side |
|---|---|
| A GitOps console | The issuer URL, a client id, and the secret of a confidential client. Some consoles accept only RS256, which the per-audience exception covers ([0006](/decisions/0006-keys-and-sealing/#named-exceptions)). |
| An application | The issuer URL, the client id, and a redirect URI that is on the client's list in sluis. |
| A gateway | The same, in the gateway's own OIDC policy; the gateway forwards the bearer. |
| An MCP server | Its resource URL, and its protected-resource metadata. |
| cert-manager | The external issuer, pointing at `ca`, with an identity the policy admits. Its CSR may have an empty subject: the identity comes from the requester. |

Every token's `aud` is exactly one registered client id, never a URL; a resource indicator selects a registered client ([0017](/decisions/0017-identity-and-sign-in/#audiences)). A confidential client's secret is generated by sluis, stored as a hash (`ClientSecret`), shown once and rotated with an overlap; a secret that IaC provides for an installation client is an `InstallationClientSecret` in a secret source. A secret that must leave sluis is stored twice, as a hash to verify and as a sealed copy that exporter@ writes to its destination ([0021](/decisions/0021-clients/#the-client-declaration)).

## What policy controls

- **Which groups may sign in to the client** (`requires`; an empty list is refused), and the token lifetime cap. A client is a `Client` in Cedar, named `<boundary>/<client id>`, and each name in `requires` is a `Grant` of the vocabulary: the schema, the standard rule and a worked example are on [Policy](/reference/policy/).
- **Redirect URIs and sign-out pages**, per client. A loopback redirect may differ in its port, for native apps.
- **Resources.** A resource is a declared URL with its own `requires` and lifetime cap, matched exactly; an undeclared or unentitled resource is refused. Clients that describe themselves with an HTTPS URL (a client identity document) are admitted only from allow-listed hosts, and only to the groups the document gate names ([0021](/decisions/0021-clients/#self-described-clients)).
- **Long-running agents** get a session class with a longer chain, shorter tokens and a consent page that is never silent ([0018](/decisions/0018-sessions/#agent-sessions)).
- **Groups in the token** are narrowed to the groups the audience requires.

## What is audited

Every sign-in and its client, every token exchange and its audience, every consent, every certificate issued, every refusal. A client secret's creation, rotation and deletion are recorded without the value.

## Setup

Names and keys are [illustrative](/integrations/#examples-are-illustrative).

```yaml
# InstallationClient and its resources, config kinds (example)
clients:
  gitops-ui:
    kind: confidential
    redirects: [https://deploy.example.org/auth/callback]
    requires: [platform-admin, platform-viewer]
    signing_alg: ES384
resources:
  https://mcp.example.org/metrics:
    client: mcp-metrics
    requires: [observability-user]
    ttl_cap: 5m
```

1. Declare the client and its groups.
2. Copy the secret when sluis generates it: it is shown once. `sluis clients show gitops-ui` lists its versions, never a value. Give the secret to the console as a secret of its own.
3. For an MCP server, declare the resource and serve its metadata, or put the sidecar in front of a stock server.
4. Check the sign-in with an allowed and a disallowed account.
