[key@](/reference/actors/#key) holds a boundary's keys and uses them in place ([0006](/decisions/0006-keys-and-sealing/)). This page lists every key purpose and every data key. It is generated by `just keys-write` from [`docs/architecture/keys.yaml`](https://github.com/truvity/sluis/blob/main/docs/architecture/keys.yaml) and the [actor registry](/reference/actors/); `just check-keys-page` fails while the page is stale, and `just check-registries` keeps the registries true and in agreement.

The concepts (sealing, wrapping, grants) are on [Keys](/concepts/keys/). The anchor of a purpose is its name: `/reference/keys/#token-signing`; of a data key, `/reference/keys/#tenant-data-key-pseudonym` or `/reference/keys/#boundary-data-key-grant`; the slot plan is `/reference/keys/#board-slot-plan`.

### How a data key is wrapped

- **AWS:** GenerateDataKey under the boundary's one symmetric key, with the encryption context {boundary, tenant, purpose}; only the wrapped copy is stored.
- **Board:** A software data key wrapped by ECDH P-384, HKDF-SHA384 and AES key wrap for each board's key-agreement key and for the recovery recipient; the full address is the authenticated data.
- **Backup archive:** An archive key is not a data key of a boundary and is not wrapped under the boundary's symmetric key. On AWS: GenerateDataKey under the dedicated archive KMS key, which may live in another account and which only the restore role decrypts. On a board: the same ECDH P-384 wrap as a data key, for the key-agreement keys named in the plan and for the recovery recipient.
