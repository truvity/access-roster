# Changelog

## Unreleased

- The writer's state no longer grows with the traffic. It held every record id of 14 days in one object, which a board filled to 4,178,767 bytes (64,287 ids), 15,537 below the 4 MiB the blob driver takes in a request; the next seal, and then the adoption of the entries a crash left, were refused (`blob put: resource_exhausted: request body size exceeds limit 4194304`) and the writer restarted in a loop. The state now holds at most about 1,280 recent ids and names write-once segments below `state/seen/` that hold the older ones, one hour of UUIDv7 time each; a check reads the segments of the id's hour only, and a segment that is missing or changed stops the writer with an error that names it. A state of the old format is read once, and the first commit after a start spills it, so a board in the loop recovers by itself on its next start, without a hand action and without losing or doubling an entry (REQ-AUDIT-178, REQ-AUDIT-179, ADR 0029). **Breaking:** a record id must be a lower-case UUIDv7, as ADR 0029 always said; a message whose record time or id time is older than 14 days, more than an hour ahead of the writer's clock, or whose id time is more than two minutes from its record's, is quarantined (`stale`, `future`, `schema`); the state is of format 2, which a writer of the first format refuses, so a rollback after the first commit cannot start; and the writer forgets ids only on a clock that the kernel calls synchronised and that has not stepped, and persists nothing from the clock that could block the log. The Go and Rust emitter kits follow the clock again when the last id is more than a minute ahead of it. A damaged segment stops the writer until the object is restored; no tool rebuilds one yet. The deploy's "every unit is up" is a point-in-time check (`docs/runtimes/bare-metal.md`).
- The boards deploy reads the lock of a card board from its card driver, with the new read-only `sluis node status NODE` (`node NODE is locked` or `unlocked`; no PIN is read, sent or printed), and not from a journal (REQ-DEPLOY-043). `SLUIS-BOARD-STATE: ok` now means every unit is up and the driver is unlocked; a locked board is `locked` (exit status 0, with the `boards-unlock` hint) whether its units are all active or only the ones that wait for key@ restart, and a unit with a fault of its own, or a lock that cannot be read, is `failed`. `boards-status` prints `board <board>: locked` or `unlocked` for each board, and `boards-unlock` asks the driver again afterwards, names a unit that systemd gave up on, and fails if a unit still restarts. **Breaking** for the generated units: an actor unit has no start limit (`StartLimitIntervalSec=0`, REQ-DEPLOY-044) and backs its restarts off from 2 s to 30 s (`RestartSteps=5`, `RestartMaxDelaySec=30`, systemd 254's; the deploy drops them on an older board), where it had 40 starts in 120 s, which a unit that waited for a locked driver exhausted (`start-limit-hit`) and which no unlock undid; deploy again to apply it. The docs say that the first board of a re-signed `KeyPlan` has to be unlocked by hand, because its peers still hold the old plan.
- key@ could not publish a PIN release: its action table lacked `key.pin.release`, `key.pin.unlock` and `key.revoke`, so the blocking audit fact of a release failed (`no action "key.pin.release" in the action table`) and a locked peer stayed locked. The three are in the table (6003 / 99, named "PIN Release", "PIN Unlock" and "Revoke") and `key.revoke` is in the audit catalogue of the local installation. A blocking emit that fails still fails the call. Tests now find every `Action` constant of keyd in the source and require it in key@'s table and in the catalogue, and the same for the other Go actors.
- **Breaking** for a reader of the audit log that keys on class: `key@` records `key.data_key.make` and `key.wrap.write` as OCSF 3004 Entity Management / 1 Create, where it recorded 6003 API Activity / 1 (ADR 0030, "The class mapping": a key created is 3004; owner decision AC1 A, 2026-11-06). The action names and fields are unchanged, so the audit catalogue is too; the other facts of `key@` stay 6003. Records already in a log keep the class they were written with.
- The credential driver of store@ accepts the credentials directory that systemd 259 makes where the filesystem has ACLs (REQ-DATA-112): `root:root` `0550`, files `root:root` `0440`, and a POSIX ACL that grants the service user the read. It refused it ("the credentials directory must be owned by the uid of this process"), so store@ had no secret source and key@ and writer@ looped on `unavailable: store`. Root may own the directory and its files only when the directory is the one `$CREDENTIALS_DIRECTORY` names (the same inode once canonicalised); a `--dir` elsewhere still has to be the driver's own uid's. Group and others still cannot write, others cannot read, and a group read is allowed only for a file with an access ACL in that directory that names no user but the driver's own uid and no group that reads. `credential check` now also reads every credential in the directory by the rules of a read and prints no value. The boards deploy now waits up to 60 s for each unit to be `active (running)` with a restart counter that has not changed for about 6 s, and fails a unit that restarts, with the last lines of its journal since the start; a card board that is only locked, waiting for its PIN (the state line `SLUIS-BOARD-STATE: locked`, and only when every other unit that has not settled depends on key@), ends `locked` with exit status 0 and names `boards-unlock` (it was a failure, and "verify: ok" only ever meant that the unit files read well). The os-containers CI jobs run the real credential driver in its unit.
- The `Workload` entity of the policy schema has two new optional attributes, `event` (GitHub's `event_name`) and `ref_type`, and the built-in layer forbids `artifact.sign` for a workload whose ref begins `refs/pull/`, whose event begins `pull_request` (`pull_request_target` included) or is `issue_comment`, `workflow_run` or `merge_group` (owner decision W1 A, 2026-11-06: these can run pull-request code), or that comes from `github-oidc` with no event (REQ-WORKLOAD-007), whatever the operator's policy permits. `exchange` reads the job claims of a verified GitHub Actions token (`repository`, `ref`, `ref_type`, `event_name`, `environment`) and refuses a `github-oidc` proof with no `event_name`. The signing API does not ask `policy` yet (#890): the guard holds from the first question. **Breaking:** `exchange` now answers `invalid_request` with the reason `claims` to a `github-oidc` proof that has no `event_name` (GitHub sends one in every token). The built-in forbid affects no existing policy that is not about `artifact.sign` for a pull request. The local installation's vectors carry `event: push` on their `github-oidc` workloads for realism; `cedar run-tests` checks them against `local.cedar` only, so the built-in rule does not apply to them and the change was not required.
- The writer and `sluis audit verify` take the checkpoint body, the tile paths and the tile entries of the audit log from `filippo.io/torchwood` and `golang.org/x/mod/sumdb/note`, and keep only the signature type 0x02 key and the adapter that has key@ sign (REQ-SEC-018, partly). Nothing on the wire changes: logs written before still verify, and logs written now verify with the former reader (tests/testdata/audit-log/old-writer). The `checkpoints/<size>` history is specified on [Checkpoint history](docs/reference/checkpoint-history.md), with limits that `audit verify` now enforces: names of at most 19 digits and checkpoint files of at most 1 MiB (`.name`, `.length`); the number of checkpoints has no limit, and `audit verify` reads the directory in batches, one file at a time, in ascending order of size, so the same log always gives the same refusal. A checkpoint with a blank extension line, which `audit verify` took before, is now refused as `.format`.
- The boards deploy (`deploy/boards`) is ready for fresh Ubuntu 26.04 and Rocky 10 boards. `just boards-rqlite` installs rqlite on each board from the upstream v10.6.6 release package, pinned by sha256 in `deploy/boards/rqlite.pins`, with a drop-in of `rqlited.service` that sets the addresses and, on every node, `-bootstrap-expect N` and `-join` with the Raft addresses of all N boards (no node can start a cluster of its own, so a wiped board rejoins the cluster of the others; the node id is the Raft address), starts all nodes and then waits for each to be a ready voter and for `/nodes` to hold N nodes; the store drivers wait for `rqlited.service`. `just boards-unlock` gives the PIN to a board's card driver from standard input, never as an argument; `cli/sluis` is staged to `/opt/sluis/bin/cli/sluis` for it. `SLUIS_BOARD_SSH_OPTIONS` carries extra ssh arguments (a known-hosts file for a reinstalled board) into the scripts and the smoke program. `SLUIS_BOARDS_PROFILE=m1` deploys the twelve executables of the M1 spine. `boards-deploy` refuses a board without `tar` before it sends anything, and `boards-deploy` and `boards-smoke` end with an AVC check (`just boards-avc`) on a board with SELinux enforcing, which fails on an enforced denial in the domain of the units or the card service, of an executable of the deploy, or on a sluis or rqlite path, and when auditd is not recording. The key-switch guard reads the data-key count with the same bash `/dev/tcp` reader as rqlite's readiness, since the boards have no curl. `boards-undeploy` and `boards-status` look after rqlite. rqlite has no TLS and no authentication on the boards yet: put a firewall in front of ports 4001 and 4002 before any real PIN (REQ-DEPLOY-034 to REQ-DEPLOY-037).
- The Rust store client follows a kind: `Store::watch` (and `KeyRevocations::watch`) lists the kind, watches from the position of the listing and gives the changes as events, in order and once (ADR 0005, REQ-DATA-108). It reconnects from the last position with a backoff and says a break as an event. A resume point that store@ no longer holds is an explicit resync that carries the whole state (REQ-DATA-109); a value that does not decode or a malformed change ends the watch with an error. `exporter@` (#1453) will use it, and `entry` and `signer` can stop reading `KeyRevocation` and `SigningRing` for each call (#1362).
- `sluis key revoke --declaration` now confirms the revocation (ADR 0009, "Confirmation"; REQ-KEYS-088, partly: the edge purge and the static document wait for `exporter@`, #1453 and #1454). After key@ takes the declaration it fetches, as a relying party does and with no cache-buster (a plain GET, a new HTTP/1.1 connection, no proxy), the `jwks_uri` that the issuer's discovery document names (on the issuer's origin) and `entry`'s live key set from its socket, and reads both every 2 seconds for up to `--wait` (default 2 minutes) until every revoked key is absent from both in the same round. The keys are those of the signed declaration, found by `kid` and by RFC 7638 thumbprint, and the answer is read strictly (a duplicate or case-variant member is `could not tell`). It prints `confirmed absent`, `still listed` or `could not tell` for each address, with the issuer, its source and the number of keys read, then warnings, then `confirmed` (exit 0) or `not confirmed` (exit 5, new): an address it cannot read is never counted as absent. `--issuer` defaults to the issuer that `entry` reports on its socket, `--entry-socket` to `/run/sluis/entry/<boundary>.sock`, so the command is run on a node that runs `entry`; a clean result is one sample from this host and this node. `--check` looks again without delivering anything. Before this the command always printed `not confirmed`.
- `sluis config explain DIR --bootstrap FILE [--field PATH]` prints what each setting of the bootstrap file and of the signed config documents resolves to, with its storage class, the layer that set it (`bootstrap`, `config` or `built-in`), its version (the `seq` of the document) and its source (the document as the audit fact of a start names it, `Kind:seq:sha384`) (REQ-OPS-023, partly: the `--live` layers and the built-in layer of the documents are not built, #1450). It runs the store executable as a helper, like `config check` (`store check --validate DIR --explain`), and explains only a set that passes its checks; a set that fails prints the failed checks and exits 3. It fails closed: store@ holds a closed table of the fields of each kind with the way each is printed, and a field it does not list is printed as its SHA-384. A credential (`secret` of an `Upstream` or an `InstallationClient`) is printed as its reference and marked; a URL has no query and no fragment; a public key of the slot map is its pin; a value longer than 256 bytes or with a control character, an invisible format character or a line separator, such as the Cedar text, is its SHA-384 (`digest: true` in JSON); a duration is shown in its largest whole unit. `--field PATH` limits the output to a subtree and a path that names nothing is a usage error. `--output json` prints `fields` beside `checks`. **Breaking:** store@ refuses at load, and `config check` with it, a URL with user information (`user:password@host`) in a boundary issuer, an upstream issuer, an exchange trust issuer or key set, or a client redirect; no fixture or example used one.
- `signer` and `entry` act on a revoked token-signing key at once (ADR 0041, REQ-KEYS-106, REQ-KEYS-107): the key set they serve lacks every kid that `KeyRevocation` lists (`entry` rebuilds its documents at most every five seconds), and `signer` never adds a revoked key to its ring, never promotes it, and refuses a `SignToken` with it on the next call (the reason `key_revoked`), where the ring was looked at again only every ten seconds. "At once" is for these two actors only: a relying party may still accept the revoked kid from its copy of `/jwks` for the key set's `max-age` (300 s) plus the edge copy, which `exporter@` is to purge (not built, #1454; `sluis key revoke` now checks for it, REQ-KEYS-088). A `KeyRevocation` that cannot be read refuses the sign and the key set (`entry` answers 503 for `/jwks` only). store@ now also requires an empty tenant for a `KeyRevocation` of a kid, a recipient or a purpose, and a tenant for a data key generation.
- A replacement for a revoked token-signing key skips the 30-minute lead time when the issuer has no live key that signs (ADR 0041, "The replacement", REQ-KEYS-089), where a one-key installation signed nothing for about 30 minutes after `sluis key revoke`. The shortcut is for the case where no key of the ring that `KeyRevocation` does not list is `active` (in practice: every `active` key is revoked); a key in a state `signer` does not know counts as signing, so a rolling upgrade cannot skip the lead time, and a normal rotation, a revoked spare and another node's live key keep it. The new key is written to the ring, `active`, with the audit reason `no_active_key` on `signer.ring.add` or `signer.ring.change`, and `signer` signs with it about 6 seconds later, not at once: `entry` keeps its built key set for 5 seconds (`sluis_store::KEY_SET_CACHE`), and no token is signed before `entry`'s `/jwks` can list the key. **Not safe to rely on yet:** the replacement signs before any relying party or edge copy has its key, a copy of `/jwks` may lack it for the key set's `max-age` (300 s) plus the edge copy, and `exporter@` does not yet purge the edge copy (#1454), so `sluis key revoke` will report a stale edge copy as `still listed` for up to the 65 minutes of the stale window (REQ-KEYS-088 is partial); do not rely on `sluis key revoke` in production yet. A relying party must fetch the key set again on an unfamiliar `kid` (OpenID Connect Core 1.0, section 10.1.1). A revoked key stays in the ring and every reader filters it; nothing removes it yet.
- `sluis config check --runtime bare-metal|serverless|kubernetes` checks the drivers of the bootstrap file against the runtime of the installation (REQ-DATA-072, REQ-OPS-009): one `installation` line for each of store@'s four ports, and a driver that does not fit, such as `rqlite` on serverless, is a `fail` that names the field (`durable.driver`) and the runtime, never the driver. No file carries the runtime, so the caller names it; without `--runtime` the check prints a `not-run` `installation` line and still exits 0 when the rest passes (a pipeline passes `--runtime` or reads each `result`), and an empty `--runtime` is a usage error. store@ does not check the drivers against a runtime at start. The drivers each port of the bootstrap file accepts are now one table in store@ (`actors/store/src/install.rs`), which the check reads. **Breaking:** store@ refuses at load, and `config check` with it, a Boundary whose `uid_block` is past the end of the uid space, where no actor of the boundary has a uid (REQ-ISO-073). A uid block that two boundaries use is not checked yet (REQ-ISO-118).
- **Breaking:** the YubiKey PIV driver verifies a PIN release itself (ADR 0006, "Touch and PIN"). It verifies the signed `KeyPlan` that key@ hands it, with the publisher keys of the bootstrap file, and keeps its highest `seq` in a `keyplan.mark` of its own. It seals the PIN only to a request that the slot map's `pin-release` key of a peer node signed, and opens only an answer signed likewise for the request it began. The driver writes and signs the request and the answer itself, and `Sign` refuses the `pin-release` purpose, so the key that signs without the PIN signs no text of key@'s. A released PIN that the card refuses stops the release in the driver's state directory, across restarts, until `sluis node unlock`. So a compromised key@ can no longer read the boundary PIN or spend the card's tries. `yubikey-piv serve` takes `--bootstrap` and `--state-dir`, which the generated unit passes. In the key-store port, `BeginPinRelease` takes the request id and returns the signed request, `SealPin` takes the request's signature and the `KeyPlan` and returns the signed answer, and `FinishPinRelease` takes the signed answer and the `KeyPlan`.
- A board deploy refuses a group of `key@`'s caller directories (`sluis-keyc-*`) that does not have its pinned number, and a sluis user that does not have its pinned uid. `systemd-sysusers` takes another number, and says nothing, when the pinned one is taken, and the numbers sit in systemd's dynamic range (the uids of every uid block but 0). The deploy checks before it writes anything, and again right after `systemd-sysusers`, and names the user or group that holds the number; a board without `getent`, or whose `getent` cannot read the users and groups, is refused too. A board that switches its key driver is checked before it is marked pending, so a refused board is left unmarked. Free that number on the board, then deploy again.
- Each caller's directory of `key@` (`/run/sluis/key/<boundary>/<caller>`) has a group of that caller's own, which only the caller joins: number uid plus 700, named `sluis-keyc-<ordinal>-<boundary>` on a board. It had the caller's own group, which the callers of that caller also join to reach its socket, so they could open the directory and only `key@`'s peer check refused them. Regenerate the units and the Compose project (`just units-gen compose-gen`); a deploy, or `just local-up`, applies the new groups.
- `sluis config check DIR --bootstrap FILE` validates a bootstrap file and the signed config documents in `DIR` offline, with store@'s own code: it runs the store executable of the same release as a helper (`store check --validate DIR`), prints one `ok`, `fail` or `not-run` line per check (or the `checks` list with `--output json`) and exits 3 when one fails. A failure names the kind, the step and the field path, never a value. The CLI finds `store` with `--helper`, `SLUIS_STORE_HELPER`, at `../libexec/sluis/actors/store` or beside itself, and refuses a `store` of another release; `config check` runs on Linux only. **Breaking:** store@ now refuses at load a set whose Boundary does not declare `GrantVocabulary`, an `InstallationClient` `ttl_cap` above one hour, and a `KeyPlan` `cache_ttl` above one hour, which key@ now refuses when it reads the plan too.
- `sluis key revoke` revokes keys by their key ids (ADR 0041, "The declaration"). It writes a key revocation declaration (`--kid`, repeated, and `--reason`), which the publisher signs as a `KeyRevocationDeclaration` with the key that signs the `KeyPlan` (on the boards: `go run ./tools/harness/sign-config -key-dir .cache/boards/publisher -declaration FILE -declaration-out FILE.jws`), and then delivers the signed declaration, as root on any node, to key@'s new admin socket `/run/sluis/key/<boundary>/admin.sock`. key@ verifies the signature under the publisher keys of its bootstrap file, refuses a replay or an older `seq` (it keeps the highest, with its digest, in `<state-dir>/keyrevocation.mark`), a declaration for another boundary and a key id it does not know (a signing key it holds, or a token key of any node in `SigningRing`), and writes one `KeyRevocation` item per key, with an audit fact that names the keys, the reason and the publisher key. Neither the token keys nor sign-in are needed. Delivering the last declaration again is a retry: a declaration that a store@ failure stopped half way is refused as `partial`, the command prints which keys are revoked and which are not yet, and the same declaration completes it. `--allow-unknown` lets the publisher revoke keys that key@ does not know (a lost board's own keys), which the audit fact marks unknown. The fact also names the node and the uid that delivered the declaration. **Breaking:** a revocation names keys and never a purpose, so key@ no longer refuses the keys of a purpose by their age; the YubiKey PIV driver no longer records when it generated a key, `yubikey-piv serve` no longer takes `--state-dir`, and its unit no longer waits for `time-sync.target` (regenerate the units: `just units-gen`).
- A board whose YubiKey PIV driver starts locked gets its PIN from an unlocked peer through the store (ADR 0006, "Touch and PIN"): it writes a `PinReleaseRequest` signed by its slot `87` key, and a peer that finds it listed in the `KeyPlan`, not revoked, fresh, attested and signed answers with a signed `PinRelease`, which the locked board verifies before its card is given the PIN, once. The PIN never leaves the card drivers, which seal and open it; a boundary has one PIN. The `KeyPlan` carries a slot map (`slot_map`: each node's slots, public keys and attestations) under the publisher's signature; `key@ check` prints the node's entry as `slot map: {...}`, `just boards-recipients` collects it into `$SLUIS_BOARDS_STATE/slot-map`, and `just boards-prepare` signs it in and adds the `pin-release` purpose to the boards' `KeyPlan`. **Breaking** for a driver of the key-store port: it gains `Attest`, `VerifyAttestation`, `BeginPinRelease`, `SealPin` and `FinishPinRelease` (the software driver refuses them by reason). The audit catalogue gains `key.pin.release` and `key.pin.unlock`.
- A board whose own pin-release key, wrapping key or recipient is revoked releases no PIN to a peer. key@ checks `KeyRevocation` for its own keys before it calls the card driver, refuses each request with the reason `self-revoked`, and audits a refusal. Before, it sealed and signed an answer and audited `key.pin.release`, although the requester then refused the answer.
- store@ serves `Watch`, the Kubernetes list-watch contract (ADR 0005). A change carries the address, the type and the version, and the value is read at delivery; an item that is gone, expired included, is a delete with no value. Every change carries its log sequence and a consumer dedupes by it (a re-created item starts at version 1 again, so a version is not an identity). Delivery is at-least-once, in the order of the change log. `List` returns a `resume_point` to watch from; an idle watch sends a bookmark every 30 seconds; a caller has at most 16 watches; a resume point the log no longer holds is `failed_precondition` / `resume_point_expired`. A config watch begins with the full snapshot, as puts and then a bookmark: replace your state for that kind with the items received before the first bookmark. Its later changes carry no sequence (resume point 0), and a consumer applies every one. **Breaking** for a driver of the item port: `QueryResponse.log_head` is new, the change log starts with a marker row, the sweeper writes a delete row for the expiry of an item written with a log row, and the rqlite schema is version 2 (an `items.logged` column). The rqlite driver keeps the change log for one hour by default (`--changelog-retention`, at most seven days; it was 24 hours). A database made by an earlier build is refused with a message that says how to recreate it: a development installation runs `just local-down` and `just local-up`, a board runs `SLUIS_PURGE_STATE=1 just boards-undeploy` and `just boards-deploy`.
- **Breaking:** `adapter-upstream-oidc` holds no credential of its own. It reads the client secret of an `Upstream` through store@ for each call, as the secret kind `UpstreamSecret`, which store@ serves from the secret source to that adapter alone. An `Upstream` names the credential in its new field `secret`, as an `InstallationClient` does (the local installation: `secret: upstream-workforce`). The adapter's `--credentials-dir` flag, its `LoadCredential=` line and the local `creds-adapter` volume are gone; regenerate the units and the Compose project (`just units-gen compose-gen`).
- **Breaking:** `session` pins the subject claim of each issuer with its first link (`UpstreamPin`, ADR 0019) and refuses a sign-in whose configured claim differs, where a changed claim made every known person look new. The id of an `UpstreamLink` is now a keyed hash of the issuer and the claim value only, without the claim name, so links made before this change are not found again; nothing is in production, and a development installation starts again with `just local-down` and `just local-up`.
- `store@` treats `KeyRevocation` as create only: for every actor, `key@` included, an update, a delete and an apply on an existing item are refused (REQ-KEYS-091), and `key@` writes it at no tenant and with no grant. `key@` refuses a Sign with a key that `KeyRevocation` lists by its kid (REQ-KEYS-109).
- **Breaking:** a development boundary takes a plain-http URL only on the loopback IP literal `127.0.0.1` or `[::1]`, as ADR 0011 says. store@ refuses at load an `http` boundary issuer, upstream issuer, `ExchangeTrust` issuer or `jwks_uri` on any other host, `localhost` included; it took any. The adapter and exchange no longer fetch from another address of `127.0.0.0/8` or from `::ffff:127.0.0.1`. A development upstream behind plain HTTP is reached through a loopback forwarder, as the local installation does.
- **Breaking:** an `InstallationClient` redirect must be `https`, or `http` on the loopback IP literal `127.0.0.1` or `[::1]` with any port (RFC 8252 section 7.3). store@ refuses any other plain-http redirect at load, `http://localhost` included, in every environment, and `/authorize` never redirects to one; a staging or production boundary now accepts a public native client's loopback redirect, and only that one, as ADR 0011 says.
- **Breaking:** `/authorize` answers a request with a scope it does not serve with `error=invalid_scope` on the client's redirect URI, where it dropped the scope and signed the person in. Only `openid`, `profile` and `email` are served.
- **Breaking:** the subject claim of an upstream ID token is at most 255 bytes (255 ASCII characters, the bound of OpenID Connect Core section 2); the adapter took 256. An upstream that sends a longer value now fails the sign-in.
- `key@`'s mark files (`keyplan.mark`, `boundary.mark`) now name their kind. A mark of the earlier form (no kind line) is read once, with the kind of the file's name, and rewritten at the next start, so an install that holds one keeps its rollback protection.
- `key@` verifies the signed `Boundary` document itself, as it does the `KeyPlan`, before it applies the floor of the software key driver, and keeps its highest `seq` in `<state-dir>/boundary.mark`. A compromised store@ can no longer serve `environment: development` to relax the floor in production.
- **Breaking:** the protected header of a signed config document names its kind (`alg`, `kid`, `seq`, `kind`), and store@ refuses a document without it or for another kind. Sign the config again (`just boards-prepare` for the boards; the local installation signs at every `just local-up`). `just boards-deploy` refuses a seed signed before this change, with "re-sign: just boards-prepare". The test keys of the vectors on the signed config page changed with it. A new call, `GetSignedConfig`, returns the signed document of a config kind to the actors that read the kind, so that a reader can verify it itself.
- Requirement tracking: a record names its Product `milestone:` (a slug that `index.yaml` maps to a board option), and a test names the requirement it proves with `// verifies: REQ-...`. `just check-requirements` fails a `done` record that has no tagged test or attestation and warns about evidence on a record that is not `done` or `partial`; the status page shows the evidence-backed count per milestone and labels records placed by inference. A live record without `milestone:` is an error (`MILESTONE_REQUIRED` in `site/scripts/check-requirements.mjs` is `true`).
- `key@` verifies the signed `KeyPlan` itself and no longer takes it from store@: it fetches the signed document (`GetSignedConfig`), checks the signature against the `publishers` block of the bootstrap file, and refuses a lower `seq` than it has seen in the process. A forged `KeyPlan`, or one signed by another key, stops the start. It keeps the highest `seq` it verified in a state directory of its own and refuses a lower one after a restart. **Breaking:** key@ needs `--bootstrap /etc/sluis/bootstrap.d/<boundary>.yaml` and `--state-dir /var/lib/sluis-state/<boundary>/key`; the generated Compose project and units pass them.
- `key@` wraps a data key only to the recipients listed in the signed `KeyPlan` (`recipients`, each the RFC 7638 thumbprint of a node's wrapping key). A `KeyCertificate` in the store only supplies the key of a listed recipient, and one that is not listed is refused and audited. `key@ check` prints the node's wrapping key id and fails while a listed recipient has no key. The local installation starts in two phases to learn the id (`deploy/local/README.md`).
- The local installation's network takes a free /24 of `10.99.0.0/16`, chosen from the project name, where it took the subnet Docker picks (`172.x`), which a host firewall may drop on the way to the upstream. `SLUIS_LOCAL_SUBNET` still overrides it, and `just local-smoke` follows `SLUIS_LOCAL_TAG` as it follows `COMPOSE_PROJECT_NAME`, so a second installation can be smoked beside the first.
- A new token-signing key is published for 30 minutes before it signs, not 12 hours: the lead time follows the cache budget of the key set (`max-age` 300 s, edge time to live, a throttled refetch on an unknown `kid`, clock skew). A verifier must honour `max-age` and fetch the key set again on an unknown `kid`.
- Token exchange authenticates a confidential client: `exchange` accepts the client's secret by HTTP Basic (`client_secret_basic`) or in the body (`client_secret_post`), answers `invalid_client` alike for a wrong secret, an unknown client and a public client that sends a secret, and a confidential client may exchange the token of a public native client. `store@` serves the secret of an installation client from the secret source to `session` and `exchange`; the client's `secret` field in the config names the credential. `private_key_jwt` comes later.
- Discovery advertises `token_endpoint_auth_methods_supported` as `none`, `client_secret_basic` and `client_secret_post`, the methods the token endpoint accepts as a whole; it said `none` only. The two secret methods are accepted by the token-exchange grant, and `authorization_code` and `refresh_token` accept only `none`, because sign-in is for public clients.
- The YubiKey PIV key driver (`drivers/key/yubikey-piv`): key@'s key-store port over the keys of a board's card, with the keys of the slot plan generated on the card, their attestation verified against Yubico's root, a firmware floor of 5.7 and exclusive card access. It starts locked and takes the PIN once, on a local admin socket, with the new `sluis node unlock NODE`; a wrong PIN is never retried. The executable that talks to a card is built natively with the tag `sluis_card`.
- The status page shows build progress: requirements that are partial next to those done, issues in progress on the board next to those closed, and a Design caption that says "not built" only while nothing is done, partial or in progress.
- The audit log's checkpoints are standard C2SP signed notes (signature type 0x02): the `audit-log` key is a P-256 key that signs SHA-256, so a generic witness or checkpoint verifier checks them, and `sluis audit verify` reads only that form. The software key driver refuses a state directory that holds an older P-384 `audit-log` key: remove its `audit-log.p8` (and the log it signed) on a development installation, or run `just local-down` and `just local-up` again.
- The `sluis` command-line tool: `sluis login`, `sluis token` and `sluis audit verify`, which checks a tiled audit log offline.
- The local installation: `just local-up` builds the images and starts every merged actor and driver under Docker Compose, each as its pinned uid, with config signed by a harness publisher key and TLS from a harness CA. `just local-status`, `local-logs` and `local-down` report on it and remove it.
- Audit search on the local installation: the indexer, the reader and the audit front (`sluis-audit.dev.local.test`) run under Compose, and `just local-audit-search 'action:signer.sign'` prints the matching audit records. A new read-only blob driver, `driver-indexer-fs`, lets the indexer and the reader read the log the writer keeps.
- The local installation runs `session` and `exchange`, and `just local-person-smoke` proves the person end to end: `sluis login` signs a test user in through the identity provider (a harness fills in the form and computes the one-time password), `sluis token --audience example-app` exchanges the token (RFC 8693), and `sluis audit verify` checks the log of the run. `exchange` finds the person behind a token through `store@` and `key@`.
- The discovery document of `entry` says `request_uri_parameter_supported: false` (OpenID Connect Discovery 1.0 section 3 defaults it to true, and `/authorize` takes no `request_uri`); a golden file holds the whole document (REQ-AUTHN-006).
- **Breaking:** every unit of a board has `SocketBindDeny=any`, and every actor unit has `NoExecPaths=` for the drivers' tree (`/opt/sluis/bin/drivers`) and for the places it can write (its run and state directories, `/tmp`, `/var/tmp`, `/dev/shm`), so every unit asks systemd to deny a TCP or UDP bind and no actor can run a driver or a copy of one from those places (REQ-ISO-095, REQ-ISO-104). Run `just boards-deploy` to install the regenerated units; a unit that connects out is not affected.
